# v0.8.0 — agent interpretation / IntentProposal

**Status:** Experimental v0.8.0 release contract for proposal-only model/agent interpretation.
**Claim class:** Experimental
**Supported platform profiles:** none

## Outcome

v0.8.0 adds a provider-neutral interpretation layer that can transform natural-language, conversational and agent-originated inputs into typed `IntentProposal` values. The proposal boundary is non-authoritative: models can suggest structured intent, assumptions and capability references, but cannot approve, authorize, plan privileged execution or execute machine changes.

The release preserves the v0.7 durable intent/Library contract and the v0.6 managed-mutation authority lifecycle. Any proposal that is accepted into authoritative intent is deterministically validated and then follows those existing boundaries.

## User-visible capability

Users and higher-level interfaces may ask an enabled model/provider to interpret a requested outcome into a structured proposal, inspect the normalized requirements, assumptions, uncertainty and provenance, reject or revise it, and explicitly accept it into durable typed intent where policy permits.

Linura remains fully operable without a model provider. Manual typed intent and non-agent workflows are first-class paths rather than degraded recovery modes.

## Implemented scope

This document is the **planned v0.8.0 release contract** and does not claim that the scope below is implemented or qualified yet. Implementation becomes releaseable only after the exact acceptance evidence in this contract exists and the release-readiness workflow marks the reviewed implementation source ready.

### IntentProposal boundary

The canonical proposal contract includes versioned structured fields for proposal identity, requested outcome, typed proposed requirements, assumptions/unresolved questions, provenance/context binding, provider/adapter identity, uncertainty where available and capability references.

Canonical proposal data is bounded, schema-validated and suitable for hashing/audit. Free-form rationale may accompany it but never overrides typed validation.

An `IntentProposal` is explicitly not:

- an approval or authorization decision;
- a privileged execution plan;
- an executor capability or credential;
- a committed desired-state change;
- a policy override;
- shell/command text to execute;
- trusted provenance merely because a model generated it.

### Provider architecture

Provider-specific APIs, authentication, streaming, tool syntax and transport mechanics are isolated behind adapters. Retry mechanics are not adapter-owned: an adapter may carry only the single provider invocation admitted by Linura Control and must return timeout, rate-limit or transport failure to Control without internally retrying, reissuing or starting a replacement/resume request. Every repeated provider invocation requires a fresh Control admission and remains charged against the original Control-owned aggregate budget and deadline.

The proposal contract is provider-neutral and supports deterministic mock/replay qualification plus local/offline, hosted and enterprise-managed implementations as adapters become available. Linura Control owns provider eligibility/discovery, selection, cross-adapter scheduling, aggregate deadlines/budgets, timeout/cancellation policy, retry/fallback/advisor admission, caching/coalescing and aggregation. The agent runtime executes only a bounded Control-admitted attempt for one selected adapter and cannot autonomously select, retry, fallback, reset aggregate budgets or aggregate providers/advisors.

Linura Control constructs the bounded semantic projection before it crosses into the agent runtime. Raw secret-bearing Library, observation, retrieval or user context is not handed to the runtime for filtering. Secret values, privileged tokens, authority credentials and protected secret-bearing fields are removed before the runtime/provider boundary; only protected references/handles or intentionally non-secret metadata may cross where semantically required.

Provider credentials and secret values remain outside proposal payloads. Runtime/adapter diagnostics and audit records must not expose secret-bearing source context or arbitrary provider response bodies.

When offline mode is active, a network-required adapter must be rejected before adapter invocation or transport initialization. Provider selection, discovery, health-check, fallback, authentication, DNS and socket setup must remain unable to trigger network activity. Release qualification must prove this with deterministic invocation/transport traps whose counters remain zero.

### Deterministic acceptance path

Before a proposal becomes durable authoritative intent, Linura must use the dedicated v0.8 Linura Control-owned acceptance path. That path:

1. validates proposal schema/version, bounded content and canonical digest;
2. obtains the authenticated `Principal` independently from trusted transport/session state and treats proposal `Actor` data as provenance only;
3. re-establishes current authority-bearing observation, policy, Library, capability-registry and existing-intent dependencies;
4. re-checks time-based observation freshness using trusted Control time, reacquiring authoritative observation where a validity window expired and failing closed if fresh evidence cannot be established;
5. derives the current Control-owned context binding and requires exact equality with the proposal binding;
6. resolves referenced capabilities only against the current Control-owned local registry;
7. requires the applicable Control-owned acceptance decision to be exact-bound to authenticated principal + proposal ID/digest + accepted context binding + durable operation identity + create/revise action + exact target identity/revision expectation;
8. acquires the authority-internal durable acceptance transaction/write-CAS guard before final authority revalidation;
9. while that durable guard is held, revalidates the complete context/freshness/capability/decision binding using monotonic fail-closed trusted Control time, normalizes every time-limited authority contributor to its exclusive first-invalid instant, derives the earliest required authority-validity deadline, captures the final-revalidation trusted-time sample as the sealed authority-time floor, and fails closed on authority-generation, target-revision, freshness, decision drift or expiry;
10. mints a transaction-scoped sealed exact-bound acceptance-commit capability carrying both the authority-time floor and authority-validity deadline;
11. consumes the capability through the authority-internal Library acceptance primitive without releasing/reacquiring the durable guard, mechanically re-sampling trusted Control time at the actual intent+acceptance-record write/CAS linearization and aborting/rolling back unless `time_floor <= now < deadline`; a backward sample below the floor is an authority-clock failure and cannot revive expired authority; and
12. atomically commits the resulting normal `Intent` in `Proposed` state together with the durable acceptance record containing the decision identity/binding, exact principal/proposal/context/operation/action/target material, authority-generation/freshness evidence, decision/approval validity evidence, sealed authority-time floor, enforced authority-validity deadline, endpoint-normalization evidence, and resulting `IntentId`/revision.

The authority-internal Library acceptance primitive is not exposed as a public `LocalLibrary`/SDK proposal-acceptance mutation and does not accept caller-constructible authority fields. Its sealed commit capability is minted only by Linura Control after final exact-bound revalidation, is not deserializable from untrusted input, is exact-bound to the durable transaction, sealed trusted-time floor and earliest required authority-validity deadline, and is consumed for one durable linearization attempt.

All time-bounded authority must remain valid at the actual durable write/CAS linearization, not merely when the capability is minted. A database-lock, scheduler or internal-I/O delay after minting that crosses the sealed deadline—whether because observation freshness or decision/approval applicability expires—must cause rollback and fresh re-entry through Linura Control rather than commit stale or unauthorized acceptance. Trusted Control time must also remain monotonic for the in-flight transaction: a post-mint backward/reset/continuity-unknown sample fails closed even when it would otherwise satisfy `now < deadline`.

The pre-v0.8 public `LocalLibrary::create_intent` operation by itself is **not** the v0.8 proposal-acceptance contract. Exact retry after a lost response/restart must return the same durable result, while conflicting reuse or substitution of proposal, context, operation, decision, action or target fails closed.

That acceptance decision authorizes only the exact durable intent create/revise operation. It does not create machine-mutation approval or executor authority. Any later external mutation flows through the v0.6 observe → plan → validate → authorize → prepare → execute → verify → commit → audit → reconcile lifecycle.

### Adversarial and stale-context handling

Prompt injection, retrieved malicious text, malformed structured output and model-generated tool/action suggestions are treated as untrusted proposal inputs. A provider cannot add its own capabilities, reduce approval requirements, suppress policy failures or manufacture trusted evidence.

Proposals are bound to relevant Control-owned context material. Stale policy, Library, capability-registry or intent state must be detected before acceptance. Observation freshness is also re-evaluated independently of revision equality: a validity window can expire without a new revision, and such evidence must be reacquired or rejected before acceptance rather than silently treated as current.

Final acceptance revalidation is serialized with the durable write/CAS transaction, and the sealed authority-time floor plus authority-validity deadline are enforced again at its actual linearization point, so concurrent authority-state drift, post-mint authority expiry, or authority-clock rollback cannot convert a valid review into stale or unauthorized persisted acceptance.

### Multi-advisor semantics

Where multiple specialist/model outputs are exposed, their provenance and material disagreement remain explicit. Linura Control owns cross-advisor scheduling, aggregate budgets and deterministic select/combine/reject policy; the runtime returns bounded per-attempt records and cannot silently initiate or aggregate additional advisors. Aggregation or consensus never constitutes authorization. Deterministic conflict handling must preserve the evidence needed to explain which proposal was selected, combined, rejected or sent back for clarification.

## Authority and security boundary

`agent_role = "proposal-only"` is the defining v0.8 authority boundary. Models and adapters receive no executor handle, policy-admin authority, human approval identity, unrestricted system tool surface or implicit user authority.

The agent runtime also receives no raw secret-bearing authority context and owns no cross-provider orchestration policy. Linura Control owns provider discovery/eligibility, selection/scheduling, deadlines and aggregate budgets, retry/fallback/advisor admission, caching/coalescing and aggregation, plus projection minimization, authenticated-principal binding, authoritative context/freshness derivation, capability-registry resolution, exact-bound acceptance authorization, durable acceptance serialization, monotonic trusted-time authority-validity normalization/evaluation and sealed acceptance-capability minting. The Linura Library durable path owns only atomic storage of the accepted intent and exact acceptance record plus mechanical enforcement of the sealed trusted-time floor and authority-validity deadline at durable linearization; it does not gain policy, approval or executor authority.

The existing privileged effect surface is not widened by this release. The only release-qualified managed external effect remains the inherited narrow managed systemd active/inactive convergence path.

## Platform and hardware scope

No Linux distribution, desktop/headless environment, physical hardware tier, virtualization platform, machine profile or fleet environment becomes a supported product profile in v0.8.0. Workstation/server/edge remain declarative target classes only.

Provider qualification environments are evidence infrastructure and do not create a platform-support claim.

## Persistence, migration and upgrade

Accepted proposal-derived intents continue to inherit the v0.7 durability, revision, causal ownership, Library, backup/recovery and portable-state substrate, but v0.8 adds a dedicated authority-internal Library acceptance record/persistence primitive that preserves exact proposal and decision lineage.

The durable acceptance record must retain the authenticated principal, acceptance-decision identity/binding, proposal ID/digest, accepted Control context binding, durable operation identity, create/revise action and target expectation, authority-generation/freshness evidence, decision/approval validity evidence, sealed trusted-time floor and enforced authority-validity deadline/endpoint-normalization evidence at linearization, and resulting intent identity/revision. Exact retry must be idempotent; conflicting reuse must fail closed.

The proposal-acceptance primitive must not become a new public SDK authority surface. A process failure before commit loses any transient sealed commit capability and requires fresh Control revalidation; a lost response after successful commit is recovered from the exact durable acceptance record without minting a duplicate intent.

Any new durable proposal or acceptance representation requiring persistence changes must use repository-defined forward migration, reject unsupported newer schemas, preserve existing v0.7 state, and be exercised through upgrade/reopen qualification before release.

## Recovery and rollback

Provider unavailability, timeout, cancellation, malformed streaming, rate limiting or adapter failure must terminate without creating partially authoritative intent or privileged action. Retry/replay semantics must not substitute different semantic proposal content under an established operation identity.

A lost response after a committed proposal acceptance must be recoverable through the exact durable acceptance binding without creating a duplicate intent or reusing an acceptance decision for changed material.

If authority was valid when a sealed capability was minted but the earliest required authority-validity deadline expires before the durable write/CAS linearizes—whether due to observation freshness or decision/approval applicability—the transaction must abort with no intent/acceptance-record mutation and must re-enter Linura Control for fresh authority establishment. The same fail-closed outcome applies if the post-mint trusted-Control time sample rolls backward below the sealed floor or monotonic continuity cannot be established.

The manual/no-provider path remains available independently of provider recovery. Proposal rejection, cancellation or provider failure requires no machine rollback because proposals have no execution authority; once a proposal is explicitly accepted into authoritative intent, later recovery follows the existing v0.7 persistence and v0.6 managed-mutation contracts.

## Compatibility boundary

Proposal schemas and provider adapters remain Experimental and may evolve before 1.0 when implementation, migrations/contracts, tests and documentation change coherently. Unsupported newer proposal schema versions and malformed provider output are rejected rather than guessed or silently downgraded.

Provider-specific features may be exposed only behind the provider-neutral proposal boundary. A provider capability must not silently become part of Linura's authority or portability contract merely because one adapter supports it.

## Known limitations and unsupported states

- Model interpretation is optional; no provider availability SLA is claimed.
- Agent/model authority remains proposal-only.
- No arbitrary tool execution, shell command execution or direct privileged mutation is released.
- No supported distribution or machine profile exists yet.
- Hosted/enterprise providers may have provider-specific privacy, rate-limit and availability constraints outside Linura's control.
- Semantic correctness of model suggestions is not trusted; deterministic validation and review remain mandatory.
- No generic multi-agent autonomous orchestration or fleet authority is claimed.

## Explicit non-goals

v0.8.0 does not claim autonomous agents, unattended root access, generic computer-use authority, policy bypass, direct executor access, universal provider equivalence, a supported reference environment, First Boot, Stable API compatibility or production readiness.
