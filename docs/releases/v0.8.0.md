# v0.8.0 — agent interpretation / IntentProposal

**Status:** Experimental v0.8.0 release contract for proposal-only model/agent interpretation.
**Claim class:** Experimental
**Supported platform profiles:** none

## Outcome

v0.8.0 adds a provider-neutral interpretation layer that can transform natural-language, conversational and agent-originated inputs into typed `IntentProposal` values. The proposal boundary is non-authoritative: models can suggest structured intent, assumptions and capability references, but cannot approve, authorize, plan privileged execution or execute machine changes.

The release preserves the v0.7 durable intent/Library contract and the v0.6 managed-mutation authority lifecycle. Any proposal that is accepted into authoritative intent is deterministically validated and then follows those existing boundaries.

## User-visible capability

Users and higher-level interfaces may ask an enabled model/provider to interpret a requested outcome into a structured proposal, inspect the normalized requirements, assumptions, uncertainty and provenance, reject or revise it, and explicitly accept it into durable typed intent where policy permits.

Linura remains fully operable without a model provider. Manual typed intent and non-agent workflows are first-class paths rather than degraded recovery modes.

## Implemented scope

This document is the **planned v0.8.0 release contract** and does not claim that the scope below is implemented or qualified yet. Implementation becomes releaseable only after the exact acceptance evidence in this contract exists and the release-readiness workflow marks the reviewed implementation source ready.

### IntentProposal boundary

The canonical proposal contract includes versioned structured fields for proposal identity, requested outcome, typed proposed requirements, assumptions/unresolved questions, provenance/context binding, provider/adapter identity, uncertainty where available and capability references.

Canonical proposal data is bounded, schema-validated and suitable for hashing/audit. Free-form rationale may accompany it but never overrides typed validation.

An `IntentProposal` is explicitly not:

- an approval or authorization decision;
- a privileged execution plan;
- an executor capability or credential;
- a committed desired-state change;
- a policy override;
- shell/command text to execute;
- trusted provenance merely because a model generated it.

### Provider architecture

Provider-specific APIs, authentication, streaming, tool syntax and retry semantics are isolated behind adapters. The proposal contract is provider-neutral and supports deterministic mock/replay qualification plus local/offline, hosted and enterprise-managed implementations as adapters become available.

`linura-control` constructs the bounded semantic projection before it crosses into the agent runtime. Raw secret-bearing Library, observation, retrieval or user context is not handed to the runtime for filtering. Secret values, privileged tokens, authority credentials and protected secret-bearing fields are removed before the runtime/provider boundary; only protected references/handles or intentionally non-secret metadata may cross where semantically required.

Provider credentials and secret values remain outside proposal payloads. Runtime/adapter diagnostics and audit records must not expose secret-bearing source context or arbitrary provider response bodies.

### Deterministic acceptance path

Before a proposal becomes durable authoritative intent, Linura must use the dedicated v0.8 `linura-control`-owned acceptance orchestration path. That path:

1. validates proposal schema/version, bounded content and canonical digest;
2. obtains the authenticated `Principal` independently from trusted transport/session state and treats proposal `Actor` data as provenance only;
3. re-establishes current authority-bearing observation, policy, Library, capability-registry and existing-intent dependencies;
4. re-checks time-based observation freshness using trusted time obtained inside `linura-control`, reacquiring authoritative observation where a validity window expired and failing closed if fresh evidence cannot be established;
5. derives the current `linura-control`-owned context binding and requires exact equality with the proposal binding;
6. resolves referenced capabilities only against the current `linura-control`-owned local registry;
7. requires the applicable `linura-control`-owned acceptance decision to be exact-bound to authenticated principal + proposal ID/digest + accepted context binding + durable operation identity + create/revise action + exact target identity/revision expectation;
8. converts the proposal only into a normal `Intent` in `Proposed` state; and
9. invokes the dedicated `linura-library` acceptance persistence operation so the intent transition and durable acceptance record commit atomically with the decision identity/binding, all exact proposal/context/operation/target material, and the resulting `IntentId`/revision.

The pre-v0.8 generic `LocalLibrary::create_intent` operation by itself is **not** the v0.8 proposal-acceptance contract. The dedicated `linura-control` orchestration + `linura-library` atomic persistence path is required so exact retry after lost response/restart returns the same durable result and conflicting reuse or substitution of proposal, context, operation, decision or target fails closed.

That acceptance decision authorizes only the exact durable intent create/revise operation. It does not create machine-mutation approval or executor authority. Any later external mutation flows through the v0.6 observe → plan → validate → authorize → prepare → execute → verify → commit → audit → reconcile lifecycle.

### Adversarial and stale-context handling

Prompt injection, retrieved malicious text, malformed structured output and model-generated tool/action suggestions are treated as untrusted proposal inputs. A provider cannot add its own capabilities, reduce approval requirements, suppress policy failures or manufacture trusted evidence.

Proposals are bound to relevant `linura-control`-owned context material. Stale policy, Library, capability-registry or intent state must be detected before acceptance. Observation freshness is also re-evaluated independently of revision equality: a validity window can expire without a new revision, and such evidence must be reacquired or rejected before acceptance rather than silently treated as current.

### Multi-advisor semantics

Where multiple specialist/model outputs are exposed, their provenance and material disagreement remain explicit. Aggregation or consensus never constitutes authorization. Deterministic conflict handling must preserve the evidence needed to explain which proposal was selected, combined, rejected or sent back for clarification.

## Authority and security boundary

`agent_role = "proposal-only"` is the defining v0.8 authority boundary. Models and adapters receive no executor handle, policy-admin authority, human approval identity, unrestricted system tool surface or implicit user authority.

The agent runtime also receives no raw secret-bearing authority context. `linura-control` owns projection minimization, authenticated-principal binding, authoritative context/freshness derivation, capability-registry resolution, exact-bound acceptance authorization and acceptance orchestration. `linura-library` owns only the atomic durable acceptance-record + resulting-intent persistence operation; it does not gain policy, approval or executor authority.

The existing privileged effect surface is not widened by this release. The only release-qualified managed external effect remains the inherited narrow managed systemd active/inactive convergence path.

## Platform and hardware scope

No Linux distribution, desktop/headless environment, physical hardware tier, virtualization platform, machine profile or fleet environment becomes a supported product profile in v0.8.0. Workstation/server/edge remain declarative target classes only.

Provider qualification environments are evidence infrastructure and do not create a platform-support claim.

## Persistence, migration and upgrade

Accepted proposal-derived intents continue to inherit the v0.7 durability, revision, causal ownership, Library, backup/recovery and portable-state substrate, but v0.8 adds a dedicated `linura-library` acceptance record/persistence operation that preserves exact proposal and decision lineage.

The durable acceptance record must retain the authenticated principal, acceptance-decision identity/binding, proposal ID/digest, accepted `linura-control` context binding, durable operation identity, create/revise action and target expectation, and resulting intent identity/revision. Exact retry must be idempotent; conflicting reuse must fail closed.

Any new durable proposal or acceptance representation requiring persistence changes must use repository-defined forward migration, reject unsupported newer schemas, preserve existing v0.7 state, and be exercised through upgrade/reopen qualification before release.

## Recovery and rollback

Provider unavailability, timeout, cancellation, malformed streaming, rate limiting or adapter failure must terminate without creating partially authoritative intent or privileged action. Retry/replay semantics must not substitute different semantic proposal content under an established operation identity.

A lost response after a committed proposal acceptance must be recoverable through the exact durable `linura-library` acceptance binding without creating a duplicate intent or reusing an acceptance decision for changed material.

The manual/no-provider path remains available independently of provider recovery. Proposal rejection, cancellation or provider failure requires no machine rollback because proposals have no execution authority; once a proposal is explicitly accepted into authoritative intent, later recovery follows the existing v0.7 persistence and v0.6 managed-mutation contracts.

## Compatibility boundary

Proposal schemas and provider adapters remain Experimental and may evolve before 1.0 when implementation, migrations/contracts, tests and documentation change coherently. Unsupported newer proposal schema versions and malformed provider output are rejected rather than guessed or silently downgraded.

Provider-specific features may be exposed only behind the provider-neutral proposal boundary. A provider capability must not silently become part of Linura's authority or portability contract merely because one adapter supports it.

Publication requires:

- dedicated v0.8 proposal/agent qualification covering schema, provider conformance, `linura-control`-owned projection minimization, time-based observation freshness, current-context/capability resolution, exact-bound acceptance authorization/orchestration, `linura-library` atomic acceptance idempotency/provenance, adversarial input and no-authority invariants;
- inherited mandatory v0.6/v0.7 lifecycle, persistence, Library, recovery and authority qualifications;
- a reviewed tree-identical metadata-only release authorization;
- Trusted Release Proof bound to the exact authorized source;
- deterministic sealed release construction, checksums, SPDX SBOM, build environment, proof receipt and provenance/attestations;
- independent byte-for-byte reproduction of distributable binaries;
- promotion only after proof success;
- tag-last immutable `v0.8.0` publication without rebuilding the sealed payload;
- independent published-release verification;
- protected reviewed post-release closure before roadmap advancement.

Development or implementation-head runs are supporting evidence only and never substitute for release-authorization proof.

## Known limitations and unsupported states

- Model interpretation is optional; no provider availability SLA is claimed.
- Agent/model authority remains proposal-only.
- No arbitrary tool execution, shell command execution or direct privileged mutation is released.
- No supported distribution or machine profile exists yet.
- Hosted/enterprise providers may have provider-specific privacy, rate-limit and availability constraints outside Linura's control.
- Semantic correctness of model suggestions is not trusted; deterministic validation and review remain mandatory.
- No generic multi-agent autonomous orchestration or fleet authority is claimed.

## Explicit non-goals

v0.8.0 does not claim autonomous agents, unattended root access, generic computer-use authority, policy bypass, direct executor access, universal provider equivalence, a supported reference environment, First Boot, Stable API compatibility or production readiness.
