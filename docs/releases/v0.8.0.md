# v0.8.0 — agent interpretation / IntentProposal

**Status:** Experimental v0.8.0 release contract for proposal-only model/agent interpretation.
**Claim class:** Experimental
**Supported platform profiles:** none

## Outcome

v0.8.0 adds a provider-neutral interpretation layer that can transform natural-language, conversational and agent-originated inputs into typed `IntentProposal` values. The proposal boundary is non-authoritative: models can suggest structured intent, assumptions and capability references, but cannot approve, authorize, plan privileged execution or execute machine changes.

The release preserves the v0.7 durable intent/Library contract and the v0.6 managed-mutation authority lifecycle. Any proposal that is accepted into authoritative intent is deterministically validated and then follows those existing boundaries.

## User-visible capability

Users and higher-level interfaces may ask an enabled model/provider to interpret a requested outcome into a structured proposal, inspect the normalized requirements, assumptions, uncertainty and provenance, reject or revise it, and explicitly accept it into durable typed intent where policy permits.

Linura remains fully operable without a model provider. Manual typed intent and non-agent workflows are first-class paths rather than degraded recovery modes.

## IntentProposal boundary

The canonical proposal contract includes versioned structured fields for proposal identity, requested outcome, typed proposed requirements, assumptions/unresolved questions, provenance/context binding, provider/adapter identity, uncertainty where available and capability references.

Canonical proposal data is bounded, schema-validated and suitable for hashing/audit. Free-form rationale may accompany it but never overrides typed validation.

An `IntentProposal` is explicitly not:

- an approval or authorization decision;
- a privileged execution plan;
- an executor capability or credential;
- a committed desired-state change;
- a policy override;
- shell/command text to execute;
- trusted provenance merely because a model generated it.

## Provider architecture

Provider-specific APIs, authentication, streaming, tool syntax and retry semantics are isolated behind adapters. The proposal contract is provider-neutral and supports deterministic mock/replay qualification plus local/offline, hosted and enterprise-managed implementations as adapters become available.

Provider credentials and secret values remain outside proposal payloads. Adapter diagnostics and audit records must not expose them.

## Deterministic acceptance path

Before a proposal becomes durable authoritative intent, Linura validates schema/version, bounded content, referenced capabilities, context/provenance revision and semantic constraints. Unknown or contradictory authority-bearing fields fail closed.

Acceptance is an explicit operation through the v0.7 durable intent/idempotency interface. Required human/policy decisions remain separate evidence. Any later external mutation flows through the v0.6 observe → plan → validate → authorize → prepare → execute → verify → commit → audit → reconcile lifecycle.

## Adversarial and stale context handling

Prompt injection, retrieved malicious text, malformed structured output and model-generated tool/action suggestions are treated as untrusted proposal inputs. A provider cannot add its own capabilities, reduce approval requirements, suppress policy failures or manufacture trusted evidence.

Proposals are bound to relevant context revisions. Stale observation, policy, Library, capability-registry or intent context must be detected and revalidated before acceptance rather than silently reinterpreted against newer authority-bearing state.

## Multi-advisor semantics

Where multiple specialist/model outputs are exposed, their provenance and material disagreement remain explicit. Aggregation or consensus never constitutes authorization. Deterministic conflict handling must preserve the evidence needed to explain which proposal was selected, combined, rejected or sent back for clarification.

## Authority and security boundary

`agent_role = "proposal-only"` is the defining v0.8 authority boundary. Models and adapters receive no executor handle, policy-admin authority, human approval identity, unrestricted system tool surface or implicit user authority.

The existing privileged effect surface is not widened by this release. The only release-qualified managed external effect remains the inherited narrow managed systemd active/inactive convergence path.

## Platform and hardware scope

No Linux distribution, desktop/headless environment, physical hardware tier, virtualization platform, machine profile or fleet environment becomes a supported product profile in v0.8.0. Workstation/server/edge remain declarative target classes only.

Provider qualification environments are evidence infrastructure and do not create a platform-support claim.

## Persistence and compatibility

Accepted intents continue to use the v0.7 durable persistence, revision, causal ownership, Library, backup/recovery and portable-state contracts. Proposal schemas/provider adapters are Experimental and may evolve before 1.0 when implementation, migrations/contracts, tests and documentation change coherently.

Unsupported newer proposal schema versions and malformed provider output are rejected rather than guessed or silently downgraded.

## Recovery and provider failure

Provider unavailability, timeout, cancellation, malformed streaming, rate limiting or adapter failure must terminate without creating partially authoritative intent or privileged action. Retry/replay semantics must not substitute different semantic proposal content under an established operation identity.

The manual/no-provider path remains available independently of provider recovery.

## Required acceptance evidence

Publication requires:

- exact-head CI, Security and CodeQL for the reviewed release source;
- dedicated v0.8 proposal/agent qualification covering schema, provider conformance, staleness, adversarial input and no-authority invariants;
- inherited mandatory v0.6/v0.7 lifecycle, persistence, Library, recovery and authority qualifications;
- a reviewed tree-identical metadata-only release authorization;
- Trusted Release Proof bound to the exact authorized source;
- deterministic sealed release construction, checksums, SPDX SBOM, build environment, proof receipt and provenance/attestations;
- independent byte-for-byte reproduction of distributable binaries;
- promotion only after proof success;
- tag-last immutable `v0.8.0` publication without rebuilding the sealed payload;
- independent published-release verification;
- protected reviewed post-release closure before roadmap advancement.

Development or implementation-head runs are supporting evidence only and never substitute for release-authorization proof.

## Known limitations and unsupported states

- Model interpretation is optional; no provider availability SLA is claimed.
- Agent/model authority remains proposal-only.
- No arbitrary tool execution, shell command execution or direct privileged mutation is released.
- No supported distribution or machine profile exists yet.
- Hosted/enterprise providers may have provider-specific privacy, rate-limit and availability constraints outside Linura's control.
- Semantic correctness of model suggestions is not trusted; deterministic validation and review remain mandatory.
- No generic multi-agent autonomous orchestration or fleet authority is claimed.

## Explicit non-goals

v0.8.0 does not claim autonomous agents, unattended root access, generic computer-use authority, policy bypass, direct executor access, universal provider equivalence, a supported reference environment, First Boot, Stable API compatibility or production readiness.

## Publication evidence

Publication is established only by the protected proof-first/tag-last lifecycle: reviewed release readiness and mechanical preparation, reviewed tree-identical metadata-only release authorization, successful Trusted Release Proof and promotion, immutable tag/GitHub Release publication from the sealed payload without rebuild, independent published-release verification, and protected reviewed post-release closure.

The frozen release body intentionally contains only publication-stable scope and evidence requirements. Live terminal status is recorded separately by the repository's terminal release record, publication-evidence dossier and canonical roadmap.
