# v0.9.0 — First Boot and supported reference environment

**Status:** implementation in progress; no v0.9 release or platform-support claim yet  
**Claim class:** Experimental

## Purpose

v0.9.0 turns Linura's already-qualified deterministic authority, durable Library and proposal-only interpretation layers into the first reproducible machine-adoption path. The milestone is intentionally bounded: it must prove one exact Experimental QualificationEnvironment and one coherent First Boot/provisioning/recovery contract before Linura claims broader machine support.

The signature entry point is:

> **What do you want this computer to become?**

That question is a client experience, not an authority shortcut. Every adoption source path converges on target-machine discovery, fresh authoritative observation, fresh planning, Control-owned review/authorization, verified recovery readiness, and only then the already-canonical authority lifecycle.

ADR 0029 defines the v0.9 QualificationEnvironment and provisioning boundary while ADR 0003 remains active for the first interactive workstation PlatformProfile.

## Candidate QualificationEnvironment

The initial v0.9 candidate is deliberately narrow and reproducible:

| Field | Candidate value |
| --- | --- |
| QualificationEnvironment ID | `qualification/ubuntu-24.04-lts/amd64/qemu-tcg-headless` |
| Machine class | `server` |
| Distribution | Ubuntu 24.04 LTS |
| Architecture | `x86_64` / amd64 |
| Interaction model | headless |
| Virtualization | QEMU TCG |
| Init/service manager | systemd |
| Base image | `https://cloud-images.ubuntu.com/releases/noble/release-20260725/ubuntu-24.04-server-cloudimg-amd64.img` |
| Base-image SHA-256 | `d1940f7d69d343355e183dff1e08a59852d32e7309baa7a4bad8365b11b005ac` |

This exact shape reuses Linura's existing pinned disposable-VM acceptance substrate without redefining Linura's product platform direction. It is a **candidate QualificationEnvironment** until all v0.9 release gates succeed. While `v0.8.0` remains the current release, both the release-qualified QualificationEnvironment lane and all release-qualified PlatformProfile lists in the hardware support matrix remain empty.

The v0.9 claim is **Linura installation/adoption on this exact Linux QualificationEnvironment**. The pinned Ubuntu image is the base-environment qualification substrate; v0.9 does not thereby claim ownership or support of the preceding Linux disk partitioning, bootloader installation, full-disk takeover, dual-boot layout or bare-metal OS installation process.

The candidate does **not** claim:

- a general-purpose Linura Linux distribution installer;
- bare-metal Ubuntu support;
- full-disk or dual-boot installation;
- ARM64 support;
- desktop/workstation support;
- arbitrary cloud-provider images;
- every QEMU/KVM configuration;
- server, workstation or edge as universally supported classes;
- generic package/network/storage/firewall mutation beyond separately qualified capabilities.

Broader platform or installer support requires separate evidence and a later explicit contract.

## First Boot source model

First Boot accepts declarative source material through explicit typed source classes:

1. fresh human intent;
2. deterministic default profile;
3. local Library Setup;
4. local Library MachineProfile;
5. portable Setup import;
6. portable MachineProfile import;
7. recovery/resume checkpoint.

Portable sources require integrity binding. Library/import/default sources are **not** plans and never replay historical executor actions. Selecting or changing a source invalidates all source-derived discovery, observation, plan, review and recovery bindings.

Every non-recovery adoption path must therefore perform fresh target discovery and authoritative observation before a new plan can be reviewed.

## Provisioning and ownership modes

v0.9 distinguishes the machine from the person preparing or eventually owning it. Machine identity, installer/operator identity and owner identity are separate authority concepts.

The reference architecture must support three entry modes:

1. **interactive owner provisioning** — the eventual owner is present and proceeds through First Boot directly;
2. **prepare for another owner** — an operator establishes the bounded Linura base/provisioning state and stops at an explicit `owner-enrollment-pending` state without inventing final-owner credentials;
3. **unattended/headless provisioning** — bounded declarative provisioning input can select the machine/provisioning mode and source material without an interactive wizard.

Deferred owner enrollment must resume deterministically without replaying already-completed provisioning work. The preparer cannot transfer historical approval into the eventual owner's later plans.

Owner credentials, password material and private keys are not portable Setup/MachineProfile data and must not be retained in ordinary provisioning provenance.

## Unattended provisioning contract

The unattended path is based on a versioned, bounded, integrity-bound **Provisioning Manifest** delivered through an explicitly qualified local transport such as removable or virtual media.

The manifest is untrusted declarative input. It may select typed provisioning inputs such as:

- interactive/deferred-owner/unattended provisioning mode;
- default, Library or portable Setup/MachineProfile source;
- whether final owner enrollment is deferred;
- bounded bootstrap networking intent;
- non-secret references to separately protected credential/secret material;
- explicitly bounded host identity inputs where supported.

The manifest may not contain arbitrary shell snippets, generic commands, executor permits, approvals, policy overrides, historical action transcripts or model authority. Integrity proves which manifest bytes were supplied; it does not make those bytes trusted.

Unattended provisioning still performs local reference-profile validation, target discovery, fresh authoritative observation, fresh planning and Control-owned review/authorization. It does not create a second mutation lifecycle.

## First Boot authority boundary

`linura-firstboot` is an unprivileged client/orchestrator. Its v0.9 contract is explicitly pre-authority:

```text
source/provisioning selection
→ reference-environment discovery
→ fresh target observation
→ fresh plan binding
→ verified recovery readiness
→ non-authorizing Control submission
```

First Boot does not manufacture policy decisions or approvals. Canonical review/authorization remains inside Linura Control and consumes retained canonical plan material.

The First Boot submission carries exact source/provisioning, target/session, observation, plan and recovery identities and cannot carry execution authority.

First Boot therefore cannot:

- mint policy decisions or approvals;
- own a privileged executor handle;
- turn an `IntentProposal` into executable authority;
- treat imported Setup/Profile or Provisioning Manifest content as an action transcript;
- bypass the canonical Control authorization path;
- silently accept a plan derived from stale target evidence;
- continue from substituted source/session/observation/plan material;
- continue without verified restorable recovery readiness and native recovery escape hatch.

Any later managed effect enters the existing v0.6 canonical lifecycle and its exact authorization/prepare/execute/verify/commit/audit/reconcile boundaries.

## Bootstrap and recovery contract

For the v0.9 Linura-on-Ubuntu reference claim, the qualified machine-adoption sequence begins from the pinned, independently verified base image rather than claiming that Linura installed the underlying operating system.

The v0.9 provisioning/bootstrap path advances monotonically through:

```text
base-environment verification
→ Linura exact-source installation
→ Linura persistent-state initialization/migration
→ security-baseline assessment
→ provisioning/ownership-mode selection
→ bounded bootstrap networking if explicitly required
→ hardware/reference-environment discovery
→ source selection/adoption
→ fresh target observation
→ First Boot planning
→ recovery checkpoint verification
→ owner enrollment or owner-enrollment-pending
→ First Boot ready
```

A persisted ledger with a gap or skipped stage fails closed. Resume begins at the first incomplete stage; it never assumes a later completed stage makes an earlier stage safe. Reboot/crash/repeated-login behavior must be idempotent and must not blindly replay completed external effects.

Generic future bootstrap model stages for disk layout, encryption, base-system construction or bootloader work do not constitute a v0.9 support claim. If Linura later owns those destructive OS-installation operations, they require their own profile, policy and qualification evidence.

The v0.9 security baseline remains fail closed:

- the exact base image/source is integrity verified;
- persistent Linura state uses the qualified durability/storage contract;
- inbound firewall/default exposure remains deny-by-default;
- SSH/remote access is not automatically enabled because the profile is headless or unattended;
- untrusted package/software sources are disabled;
- any environment-level storage-at-rest requirement is explicit in the reference profile rather than falsely inferring guest full-disk encryption from the cloud-image substrate.

A First Boot readiness claim additionally requires a recovery checkpoint with an integrity digest, evidence that it is restorable, and a native recovery path independent of the First Boot UI/model/provider stack.

## Network and remote-access boundary

Offline/no-network provisioning remains a required path once all necessary local material exists.

First Boot distinguishes:

1. no-network/offline operation;
2. temporary bounded bootstrap connectivity used only for explicitly allowed acquisition;
3. final desired networking, which is ordinary managed state and must enter the normal observe/plan/review/authority lifecycle.

Remote reachability is never an implicit consequence of unattended or headless provisioning. SSH or future VPN/tailnet access requires explicit typed intent plus separately qualified security and verification behavior.

## Hardware adaptation boundary

Hardware discovery may influence compatibility and desired state, but detection does not grant mutation authority.

Hardware-specific adaptation must follow:

```text
discover
→ authoritative observation
→ supported-profile/capability resolution
→ deterministic desired state/plan
→ Control review/authority
→ narrow executor
→ independent verification
```

Linura must not introduce a generic arbitrary vendor-script escape hatch to imitate installer convenience. Unsupported or ambiguous hardware fails closed or remains explicitly outside the release support claim.

## Offline and no-model operation

The v0.9 reference experience must remain useful with no model provider and no network after required local installation material exists.

Offline/default/Library/import/unattended-local paths must not depend on hosted inference, hosted catalog synchronization or remote control. Model-assisted interpretation remains optional and proposal-only under the v0.8 boundary.

Native CLI/recovery access remains available independently of First Boot. Loss or corruption of a future graphical/conversational experience must not remove the machine's local recovery path.

## Essential reference-environment capabilities

The headless candidate keeps the required domain surface deliberately small. v0.9 qualification must prove the capabilities needed to install Linura, enter First Boot, provision/adopt, observe, review, recover and update the reference environment, including:

- systemd-backed service/lifecycle operation already inherited from v0.6;
- authoritative system/network observation required by target planning;
- deterministic local Library/profile adoption inherited from v0.7;
- optional proposal-only interpretation inherited from v0.8;
- provisioning/ownership-mode state and resume semantics;
- bounded bootstrap-network behavior and default-deny remote exposure;
- hardware/reference-environment discovery and typed compatibility handling;
- security-baseline sequencing;
- update interruption and recovery behavior;
- persistent-state migration/backup/restore across the supported upgrade path;
- native recovery access and verified recovery checkpoint behavior.

Because the first candidate is headless, desktop display/audio/theme/input/shell/Control Center are not required for the v0.9 support claim. Those surfaces remain v0.10 or later work unless separately activated and qualified.

## Installation, update and migration

The reference contract is not complete merely because `linura-firstboot` starts. Qualification must cover:

- exact-source Linura installation into the pinned candidate environment;
- restart/resume across provisioning/bootstrap stages;
- interactive-owner, deferred-owner and unattended-local entry modes;
- persistent Linura state migration from the immediately supported prior state;
- backup validation before destructive migration;
- interrupted update behavior;
- rollback/recovery behavior where the update outcome is indeterminate;
- recovery from a damaged/failed First Boot path without requiring model/network access;
- preservation of Library/intent/provenance authority semantics after migration.

A successful boot without recoverability is not sufficient v0.9 evidence.

## Implementation ownership

v0.9 activates three previously planned components:

- `linura-firstboot` — non-privileged First Boot/provisioning client and exact pre-authority Control-submission contract;
- `linura-bootstrap` — monotonic Linura installation/provisioning/readiness/recovery sequencing;
- `linura-hardware` — exact reference-profile identity, platform drift reporting and evidence-tier qualification.

`linura-firstboot` becomes a distributable binary for the v0.9 candidate. `linura-bootstrap` and `linura-hardware` remain linked/library components and are not separate release artifacts.

Control Center, desktop shell and Agent UI remain outside the v0.9 headless support boundary.

## Required qualification

v0.9 qualification must cover at minimum:

- deterministic source/provisioning-path selection and invalidation;
- interactive-owner, deferred-owner and unattended-local provisioning state;
- owner-enrollment resume without replay or preparer-authority inheritance;
- Provisioning Manifest schema/version/size/integrity validation and malicious-field rejection;
- portable source integrity binding;
- exact candidate reference-profile matching and unsupported-platform rejection;
- fresh authoritative observation requirement for default/Library/import/unattended paths;
- exact target/session/observation → plan → recovery → Control-submission binding;
- stale/substituted source/session/observation/plan rejection;
- canonical review/authorization remaining Control-owned;
- recovery checkpoint integrity, restore verification and native escape-hatch requirement;
- structural absence of execution authority in the First Boot submission;
- monotonic provisioning/bootstrap resume and skipped/out-of-order stage rejection;
- repeated first-run/reboot/crash idempotency;
- fail-closed security baseline and default-deny remote exposure;
- offline/no-model First Boot operation;
- bounded bootstrap networking and explicit transition to managed final networking;
- hardware adaptation rejection when profile/capability evidence is unsupported or ambiguous;
- pinned-image disposable VM acceptance on the exact reference candidate;
- exact host-built versus guest-installed `linura-firstboot` digest/size verification;
- install/update interruption and native recovery acceptance;
- migration/backup/restore qualification for persistent Linura state;
- immutable evidence references binding source SHA, base-image digest, VM mode, workflow run and produced evidence artifact where evidence is used to advance support status;
- inherited v0.6 managed lifecycle, v0.7 Library and v0.8 proposal-only qualifications;
- exact-source CI, Security and CodeQL;
- Trusted Release Proof, sealed reproducible construction, tag-last publication and independent Release Verification.

## Release gate

v0.9.0 is not releaseable until all of the following have exact evidence:

- [ ] `linura-firstboot`, `linura-bootstrap` and `linura-hardware` implementation matches this milestone boundary;
- [ ] ADR 0029 is reflected in implementation and qualification, including preservation of ADR 0003 for the first interactive workstation PlatformProfile;
- [ ] every First Boot source/provisioning path converges on fresh target discovery/observation and fresh planning;
- [ ] portable/Library/default/Provisioning Manifest material cannot replay authority or historical executor actions;
- [ ] interactive-owner, prepare-for-another-owner and unattended-local modes are bounded and restart-safe;
- [ ] deferred owner enrollment cannot inherit preparer credentials/approval and cannot fabricate final-owner identity;
- [ ] First Boot's final Control submission is exact-bound and structurally cannot create execution authority or policy approval;
- [ ] stale, substituted, malformed-manifest and unsupported-reference-environment paths fail closed;
- [ ] bootstrap/provisioning resume/restart and out-of-order/corrupt-ledger cases are qualified;
- [ ] fail-closed installation/security baseline and default-deny remote exposure are qualified;
- [ ] offline/no-model operation is qualified;
- [ ] bootstrap networking, when used, is explicitly bounded and cannot silently become final managed networking;
- [ ] hardware-specific adaptation remains typed/reviewed and no generic vendor-script authority path exists;
- [ ] exact candidate Ubuntu 24.04 LTS server amd64/QEMU-TCG reference acceptance succeeds;
- [ ] guest-installed exact-source First Boot binary identity is verified against the host build;
- [ ] installation, update interruption, migration, backup/restore and native recovery acceptance succeeds;
- [ ] the QualificationEnvironment support lane advances only from exact immutable v0.9 release-qualified evidence and PlatformProfile lanes remain unchanged;
- [ ] inherited v0.6/v0.7/v0.8 qualifications remain green;
- [ ] dedicated v0.9 qualification is part of Trusted Release Proof;
- [ ] metadata-only release authorization preserves the reviewed implementation tree;
- [ ] tag-last publication succeeds;
- [ ] the GitHub Release is immutable and independently verified;
- [ ] protected post-release closure alone advances `current_release` to v0.9.0 and `next_release` to v0.10.0;
- [ ] post-release cleanup deletes only exact release-owned refs under immutable leases.

Until those gates close, v0.9 remains a candidate under development and the current published platform-support claim remains the v0.8 contract: `platform_support = "none"`.
