# v0.9.0 — First Boot and supported reference environment

**Status:** released
**Claim class:** Experimental

## Purpose

v0.9.0 turns Linura's already-qualified deterministic authority, durable Library and proposal-only interpretation layers into the first reproducible machine-adoption path. The milestone is intentionally bounded: it proves one exact Experimental QualificationEnvironment and one coherent First Boot/provisioning/recovery contract before Linura claims broader machine support.

The signature entry point is:

> **What do you want this computer to become?**

That question is a client experience, not an authority shortcut. Every adoption source path converges on target-machine discovery, fresh authoritative observation, fresh planning, Control-owned review/authorization, verified recovery readiness, and only then the already-canonical authority lifecycle.

ADR 0029 defines the v0.9 QualificationEnvironment and provisioning boundary while ADR 0003 remains active for the first future interactive workstation PlatformProfile.

This shape reuses Linura's pinned disposable-VM substrate without redefining the product platform direction. The v0.9 claim is **Linura installation/adoption on this exact Linux QualificationEnvironment**. The pinned Ubuntu image is the base-environment qualification substrate; v0.9 does not thereby claim ownership or support of the preceding Linux disk partitioning, bootloader installation, full-disk takeover, dual-boot layout or bare-metal OS installation process.

The claim does **not** include:

- a general-purpose Linura Linux distribution installer;
- bare-metal Ubuntu support;
- full-disk or dual-boot installation;
- ARM64 support;
- desktop/workstation support;
- arbitrary cloud-provider images;
- KVM equivalence or every QEMU configuration;
- server/workstation/edge as universally supported classes;
- generic package/network/storage/firewall mutation beyond separately qualified capabilities.

Broader platform or installer support requires separate evidence and a later explicit contract.

## First Boot source model

First Boot accepts declarative source material through explicit typed source classes:

1. fresh human intent;
2. deterministic local default profile;
3. local Library Setup;
4. local Library MachineProfile;
5. portable Setup import;
6. portable MachineProfile import;
7. recovery/resume checkpoint.

Portable sources require integrity binding. Library/import/default sources are **not** plans and never replay historical executor actions. Selecting or changing a source invalidates all source-derived discovery, observation, plan, review and recovery bindings.

Every non-recovery adoption path therefore performs fresh target discovery and authoritative observation before a new plan is reviewed.

## Provisioning and ownership modes

v0.9 distinguishes the machine from the person preparing or eventually owning it. Machine identity, preparer/operator identity and owner identity are separate authority concepts.

The qualified architecture supports:

1. **interactive owner provisioning** — the eventual owner is present and proceeds through First Boot directly;
2. **prepare for another owner** — an operator establishes bounded Linura base/provisioning state and stops at explicit `owner-enrollment-pending` without inventing final-owner credentials;
3. **unattended/headless provisioning** — bounded declarative provisioning input selects machine/provisioning mode and source material without an interactive wizard;
4. **recovery owner resolution** — recovery sessions enter an explicit non-authorizing recovery resolution rather than dead-ending or inventing owner state.

Deferred owner enrollment resumes deterministically without replaying completed provisioning work. The preparer cannot transfer historical approval into the eventual owner's later plans.

Owner credentials, password material and private keys are not portable Setup/MachineProfile data and are not retained in ordinary provisioning provenance.

## Unattended provisioning contract

The unattended path uses versioned, bounded, integrity-bound **Provisioning Manifest v1** delivered through an explicitly qualified local transport.

The manifest is untrusted declarative input. It may select typed provisioning inputs such as:

- interactive/deferred-owner/unattended provisioning mode;
- default, Library or portable Setup/MachineProfile source;
- whether final owner enrollment is deferred;
- bounded bootstrap networking intent;
- non-secret references to separately protected credential/secret material;
- explicitly bounded host identity inputs where supported.

The manifest may not contain arbitrary shell snippets, generic commands, executor permits, approvals, policy overrides, historical action transcripts, model authority or secret values. Integrity proves which bytes were supplied; it does not make those bytes trusted.

Validated typed selections are persisted in durable provisioning state so restart cannot silently discard user intent. Exact Library object revisions are re-resolved from a protected Local Library before downstream use.

## First Boot authority boundary

`linura-firstboot` is a pre-authority client/orchestrator. Its v0.9 contract is:

```text
source/provisioning selection
→ exact reference-environment discovery
→ fresh target observation
→ deterministic fresh plan binding
→ verified recovery readiness
→ non-authorizing Control submission
```

First Boot does not manufacture policy decisions or approvals. Canonical review/authorization remains inside Linura Control and consumes retained canonical plan material.

First Boot cannot:

- mint policy decisions or approvals;
- own a privileged executor handle;
- turn an `IntentProposal` into executable authority;
- treat imported Setup/Profile or Provisioning Manifest content as an action transcript;
- bypass canonical Control authorization;
- silently accept a plan derived from stale target evidence;
- continue from substituted source/session/observation/plan material;
- continue without verified restorable recovery readiness and a native recovery escape hatch.

Any later managed external effect enters the inherited v0.6 observe → plan → validate → authorize → prepare → execute → verify → commit → audit → reconcile lifecycle.

## Bootstrap and recovery contract

For the v0.9 Linura-on-Ubuntu claim, adoption begins from the pinned independently verified base image rather than claiming that Linura installed the underlying operating system.

The durable bootstrap sequence is:

```text
base-environment verification
→ Linura exact-source installation
→ Linura persistent-state initialization/migration
→ security-baseline assessment
→ provisioning/ownership-mode selection
→ bounded bootstrap networking if explicitly required
→ hardware/reference-environment discovery
→ source selection/adoption
→ fresh target observation
→ First Boot planning
→ recovery checkpoint verification
→ owner enrollment or owner-enrollment-pending
→ First Boot ready
```

The persistent ledger is bounded, integrity checked, writer serialized and generation anchored outside the mutable bootstrap state-root domain. A gap, skipped stage, unsupported newer schema, corrupt binding or rollback against a current external anchor fails closed. Two-phase anchor staging/ledger publication/anchor finalization is crash-reconcilable.

Prepared and effect-started restart states require authoritative re-observation rather than blind replay. Exact qualification injects persistent-QEMU power loss after all 13 prepared-stage boundaries, every effect-started boundary and the two-phase commit crash windows.

Recovery checkpoints durably bind the bootstrap ledger, durable session and external generation anchor through a strict v3 manifest and component digests. Native recovery restores and verifies that bundle with both First Boot executable copies unavailable and networking/model dependence removed.

## Network and remote-access boundary

Offline/no-network provisioning remains a required path once necessary local material exists.

First Boot distinguishes:

1. no-network/offline operation;
2. temporary bounded bootstrap connectivity used only for explicitly allowed acquisition;
3. final desired networking, which is ordinary managed state and must enter the normal authority lifecycle.

Remote reachability is never an implicit consequence of unattended/headless provisioning. SSH or future VPN/tailnet access requires explicit typed intent plus separately qualified security and verification behavior.

The Q8 baseline verifies the actual nftables input base chain, active/enabled SSH-serving units, renamed units and listener-owning SSH server processes on every port, plus insecure one-line/deb822 APT overrides. Qualification-only SSH transport is removed from product observation rather than whitelisted into product semantics.

## Hardware adaptation boundary

Hardware discovery influences compatibility and desired state but grants no mutation authority.

Hardware-specific adaptation follows:

```text
discover
→ authoritative observation
→ supported-profile/capability resolution
→ deterministic desired state/plan
→ Control review/authority
→ narrow executor
→ independent verification
```

Machine binding incorporates protected machine identity plus DMI hardware UUID. Exact qualification boots a cloned prepared disk under a different hardware UUID and requires rejection of copied bootstrap history.

Unsupported or ambiguous hardware fails closed or remains outside the release support claim. v0.9 introduces no generic arbitrary vendor-script escape hatch.

## Offline and no-model operation

The reference experience remains usable with no model provider and no network after required local installation material exists. Offline/default/Library/import/unattended-local paths do not depend on hosted inference, hosted catalog synchronization or remote control.

Model-assisted interpretation remains optional and proposal-only under the v0.8 boundary. Native CLI/recovery access remains independent of First Boot, model/provider availability and future graphical/conversational surfaces.

The headless reference surface is deliberately small. v0.9 qualifies the capabilities needed to install Linura, enter First Boot, provision/adopt, observe, plan, recover and update the exact environment, including:

- systemd-backed service/lifecycle operation inherited from v0.6;
- authoritative system/network observation required by target planning;
- deterministic local Library/profile adoption inherited from v0.7;
- optional proposal-only interpretation inherited from v0.8;

- security-baseline sequencing;

- native recovery access and verified checkpoint behavior.

Desktop display/audio/theme/input/shell/Control Center surfaces remain outside the v0.9 headless claim.

## Installation, update and migration

The reference contract is not complete merely because `linura-firstboot` starts. Qualification covers:

- exact-source Linura installation into the pinned environment;
- restart/resume across every provisioning/bootstrap boundary;
- interactive-owner, deferred-owner, unattended-local and recovery modes;
- persistent Linura state migration from v0.8;
- writer-excluded WAL-safe validated backup before risky migration;
- complete released Local Library semantic-preservation fingerprinting;
- actually interrupted local `dpkg` update behavior;
- independently produced HMAC-authenticated package postcondition evidence;
- rollback/recovery when update outcome is indeterminate;
- recovery from damaged/failed First Boot without model/network dependence.

A successful boot without recoverability is insufficient evidence.
