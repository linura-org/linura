# v0.7.0 milestone — persistent intent lifecycle and local Linura Library

**Status:** implementation contract
**Claim class:** Experimental

v0.7.0 turns the v0.6 trustworthy mutation core into durable, local, user-owned configuration state. It adds persistence and reusable configuration semantics without widening Linura's privileged execution boundary, platform-support claim, or agent authority.

## Exact capability boundary

v0.7.0 may persist and manipulate declarative Linura state for:

- intents and their requirements;
- intent lifecycle transitions and lineage;
- desired-state / causal ownership records needed to explain and safely remove Linura-managed state;
- Setup revisions and composition;
- MachineProfile revisions and composition;
- portable local export/import bundles containing declarative configuration meaning;
- local authority-state backup/recovery for the Library database.

The v0.6 managed mutation boundary remains unchanged: only the already-qualified narrow managed systemd active/inactive effect may cross the privileged executor boundary. Persisting a broader desired-state record does not make the corresponding system domain executable or supported.

## Intent lifecycle contract

The canonical lifecycle remains:

`proposed -> active <-> suspended -> superseded | retired`

Every durable transition must:

1. validate the current stored revision and status;
2. reject stale writers through optimistic concurrency;
3. validate that the requested transition is legal;
4. preserve immutable lineage and transition evidence;
5. update the current projection atomically with the transition record;
6. be idempotent for an exact repeated operation identity;
7. reject operation-identity reuse with different semantic content.

`supersede` must bind the predecessor and successor explicitly. `retire` and `suspend` never authorize blind cleanup.

## Causal ownership and removal impact

Linura-managed resources may have multiple declarative owners. v0.7 must preserve enough causal ownership to distinguish:

- resources still required by another active intent;
- resources that become unowned when an intent is suspended, superseded or retired;
- resources whose ownership is ambiguous or incomplete.

Removal-impact analysis is read-only evidence. A resource may be considered cleanup-eligible only when the local causal record proves there is no remaining active owner. Unknown, corrupt, stale or incomplete ownership fails closed.

Any resulting external removal still has to enter the canonical managed-mutation lifecycle and remains limited to capabilities qualified by the release. The Library itself is not an authority shortcut.

## Local Library contract

The local Library stores immutable Setup/Profile revisions plus deterministic current projections.

A Setup revision contains reusable declarative composition, including:

- stable Setup identity and monotonically increasing revision;
- included intent definitions or references;
- included Setup revisions;
- portable constraints and hardware hints;
- required secret *references* only, never secret material.

A MachineProfile revision composes Setup revisions and/or intents for one declared machine class. Workstation/server/edge remain target classes, not platform-support claims.

History is append-only at the revision layer. Updating a Setup/Profile creates a new revision instead of rewriting prior meaning.

## Save, capture, export, import and adopt

### Save / capture

Saving preserves declarative Linura meaning. Capture from a managed machine must derive from Linura-owned causal state; it must not blindly serialize installed packages, arbitrary files, shell history or unrelated observed state.

### Portable export

Portable artifacts are deterministic, versioned and integrity-bound. They contain reusable declarative definitions and provenance required for safe adoption, but exclude:

- local approval/authorization evidence;
- executor or transaction authority;
- local audit secrets/keys;
- secret values;
- machine-private operational state.

Portable export is distinct from authority-state backup.

### Import

Import is parse/validate first and mutation second. Before persistent mutation it must validate:

- artifact format version;
- structural bounds and identifier validity;
- content integrity;
- Setup/Profile composition and cycle freedom;
- revision consistency;
- duplicate/collision behavior;
- secret-reference syntax;
- machine-class compatibility information where applicable.

Malformed, unsupported-newer, corrupt, ambiguous or cyclic input fails closed without partial adoption.

### Adopt

Adoption is deterministic and has a dry-run form. Dry-run must report at minimum:

- definitions that would be created or reused;
- local identity/revision collisions;
- missing secret references;
- machine-class mismatch where applicable;
- intents that would become proposed/active;
- unsupported desired-state capabilities that cannot currently execute.

Cross-device adoption never imports prior local authority. Imported active intent cannot manufacture executor, policy or approval authority; any resulting machine change still requires fresh local observation, planning, validation and authorization.

## Persistence, migrations and corruption handling

The local Library database must:

- use SQLite transactional semantics with foreign-key enforcement;
- use a crash-resilient journal configuration suitable for local durable state;
- carry an explicit schema version;
- migrate only through repository-defined forward migrations;
- reject databases created by unsupported newer schema versions;
- run integrity checks at open/recovery boundaries;
- make multi-record operations atomic;
- preserve idempotency and revision invariants across process restart;
- expose bounded errors rather than treating corrupt bytes as trusted state.

Migration failure must leave the last valid database recoverable rather than silently accepting a partially migrated authority state.

## Backup and recovery

Authority-state backup is a local operational backup of the Library database and is distinct from portable export. Backup/recovery must preserve revision history, lifecycle lineage, causal ownership and idempotency state.

Recovery must validate database/schema integrity before replacing the active store. Restore from an incompatible, corrupt or newer-format backup fails closed.

## Mandatory qualification

The exact v0.7 candidate must prove:

- create/read/list/history for intents, Setup revisions and MachineProfile revisions;
- legal suspend/reactivate/supersede/retire transitions;
- illegal transitions and stale expected revisions are rejected;
- exact operation retry is idempotent and semantic substitution is rejected;
- restart preserves current state, history and idempotency;
- shared-ownership impact preserves resources still owned by another active intent;
- orphan impact identifies only resources with proven zero active owners;
- incomplete/corrupt causal ownership fails closed;
- deterministic self-contained Setup/Profile export and round-trip import;
- corrupted artifact digest, malformed artifact, unsupported-newer format and cyclic composition fail before mutation;
- same-device and cross-device adoption dry-runs report collisions, missing secret references and machine-class compatibility;
- imported artifacts never contain or restore local mutation authority;
- backup/restore round trip preserves all durable Library invariants;
- corrupt/newer-schema backup is rejected without replacing the active valid store;
- crash/failure injection around transactional writes produces either the old complete state or the new complete state, never a partial projection/history pair;
- canonical CI, Security and CodeQL pass on the exact candidate;
- Trusted Release Proof incorporates the dedicated v0.7 qualification before publication.

## Explicit non-claims

v0.7.0 remains Experimental. It does not claim Stable or production support, a supported Linux distribution/machine profile, hosted Library sync, remote fleet authority, arbitrary package/file/network mutation, generic systemd management, unattended agent authority, secret synchronization, multi-machine atomicity, or a generic privileged execution surface.
