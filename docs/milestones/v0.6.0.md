# v0.6.0 milestone — complete eleven-stage managed mutation

**Status:** released
**Claim class:** Experimental

v0.6.0 is the first Linura milestone permitted to complete the canonical managed-mutation lifecycle for one deliberately narrow external effect. It does not authorize a generic apply surface, arbitrary commands, package/file/network mutation, broad systemd management, unattended agent execution, or a supported distribution/machine profile.

## Exact capability boundary

The only v0.6 managed external effect is:

- provider: `systemd`
- observation capability: `systemd.unit.observe`
- resource namespace: canonical `systemd:unit:linura-managed-*.service`
- operation: `set-active-state`
- desired postcondition: exactly `active` or `inactive`
- privileged mechanism: native systemd D-Bus `StartUnit(unit, "replace")` or `StopUnit(unit, "replace")`

No shell, arbitrary executable, environment, file path, package, unit type, generic D-Bus method, or user-selected systemd operation crosses the executor boundary.

## Canonical lifecycle

Every supported v0.6 managed effect must traverse the same authority lineage:

1. request / intent
2. observe
3. plan
4. validate
5. authorize
6. prepare
7. execute
8. verify
9. commit
10. audit
11. reconcile

`linura-control::ManagedLifecycleControl` composes this path over the existing `DurableAuthorityControl`; it is not a second policy, approval, transaction, or recovery authority.

## Authority and privilege split

The v0.6 runtime uses three distinct boundaries:

1. `org.linura.Authority1` authenticates the original system-bus caller and requests explicit administrator approval with Polkit action `org.linura.authority.manage-systemd-active-state`.
2. The dedicated unprivileged `linura-authority` service owns protected durable transaction/integrity secrets and the SQLite authority state. Human approval is converted into exact-bound Control approval only inside this trusted service.
3. `org.linura.Executor.Systemd1` remains a separately hardened root service. Its managed action `org.linura.executor.systemd.set-active-state` is default-deny and product policy grants it only to the `linura-authority` service identity. A human/admin caller cannot invoke the supported managed executor path directly.

Executor correlation material remains non-authority metadata. Only Control's successful fresh revalidation plus durable `Prepared -> Indeterminate` handoff mints the one-shot in-process authorization consumed by the authority runtime.

## Independent verification

The authority runtime composes a second `SystemdObserver` connection solely for verification. `SystemdActiveStateVerifier` receives the expected postcondition and a fresh canonical native-systemd `ObservationEnvelope`; executor receipts are never accepted as proof of machine state.

A mutation may reach durable `Committed` only after:

- exact executor dispatch correlation is retained;
- independent verification returns `Satisfied`;
- durable recovery independently re-observes the intended postcondition and transitions the exact indeterminate generation to `Verified`;
- signer-authorized commit succeeds;
- SQLite integrity/audit checks succeed; and
- reconciliation performs another independent verification plus a fresh Control plan that proves `NoChange`.

## Idempotency and ambiguity

- Exact retry of the same managed request reuses the same durable transaction identity.
- Request substitution must never reuse prior authority.
- `Prepared` authority left across restart is retired before new handoff work.
- A durable `Indeterminate` generation is never blindly replayed after restart.
- Intended-effect-absent recovery may re-prepare, but dispatch requires a new explicit invocation and a fresh one-shot handoff.
- Verification failure, stale/inconclusive evidence, conflicting post-state, executor ambiguity, or storage uncertainty remains fail-closed and recoverable through the canonical durable state machine.

## Mandatory disposable-system qualification

The exact release source must prove, on a disposable Ubuntu VM with real systemd, D-Bus, Polkit and SQLite/WAL:

- successful inactive -> active lifecycle through all eleven stages;
- successful active -> inactive lifecycle through all eleven stages;
- exact retry/idempotent committed result without duplicate dispatch;
- direct ordinary/admin caller denial at the managed executor boundary;
- unsupported unit namespace and unsupported desired state rejection before handoff;
- human approval denial before durable execution authority;
- stale observation/evidence fails closed;
- executor transport/dispatch failure does not commit;
- injected indeterminate dispatch remains durable and is reconciled instead of blindly replayed;
- process crash/restart after durable handoff preserves ambiguity and does not reconstruct approval or dispatch authority;
- verification `NotSatisfied` and `Inconclusive` do not commit;
- conflicting recovery becomes blocked rather than overwritten;
- successful commit is followed by audit integrity and no-change reconciliation;
- the independent verifier has no executor receipt input and uses a separately composed native observer.

## Release gate

v0.6.0 is not releaseable until:

- [x] canonical CI, Security and CodeQL pass on the exact candidate source;
- [x] dedicated v0.6 managed-lifecycle disposable-VM qualification passes on the exact candidate source;
- [x] Trusted Release Proof reruns all mandatory inherited v0.4/v0.5 qualifications plus the v0.6 qualification against the exact release authorization;
- [x] independent binary reproduction succeeds;
- [x] tag-last publication succeeds;
- [x] independent published-release verification succeeds;
- [x] post-release closure advances machine roadmap state only after immutable publication evidence exists.

## Explicit non-claims

v0.6.0 remains Experimental. It does not claim production readiness, a supported Linux distribution, a supported machine class/hardware profile, generic system configuration, a stable public mutation API, unattended agent authority, multi-resource atomicity, or broad systemd support.
