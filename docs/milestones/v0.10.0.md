# v0.10.0 — Complete Experimental Linura workstation

**Status:** planned / implementation not yet qualified
**Claim class:** Experimental
**Target PlatformProfile:** `arch-hyprland-v1`

## Purpose

v0.10.0 turns the trustworthy control-plane, durable intent/Library, proposal-only agent interpretation and v0.9 First Boot foundation into Linura's first **complete Experimental workstation product** on one exact PlatformProfile.

The milestone deliberately does **not** reinterpret v0.9. Ubuntu 24.04/amd64/QEMU-TCG/headless remains the release-qualified v0.9 **QualificationEnvironment** used to prove the Linura layer. It is not a PlatformProfile. v0.10 instead gives `arch-hyprland-v1` its own workstation-specific contract and evidence so that Linura can qualify its first actual PlatformProfile without claiming generic Linux desktop support.

ADR 0003 keeps the platform boundary narrow. ADR 0031 keeps all interfaces on one typed machine model and one Control authority path. ADR 0032 classifies trusted operation semantics before authority-path selection. ADR 0033 rebaselines the product scope: ordinary workstation completeness belongs in v0.10, while v1.0 is the Stable-support qualification of that already-complete product.

The machine-readable implementation ledger is `contracts/v010-workstation-slices.toml`. Its 32 required slices are part of the milestone contract; changing their meaning/count/order requires an explicit reviewed rebaseline rather than silent roadmap drift.

## End-user outcome

A v0.10 experimental user on the qualified workstation profile must be able to complete this loop without hidden privileged shortcuts:

```text
install/adopt Linura
→ First Boot / owner enrollment
→ inspect machine state
→ express intent manually or through proposal-only agent assistance
→ inspect deterministic plan and risk/authority requirements
→ approve when policy requires it
→ execute only supported typed effects
→ independently verify resulting state
→ inspect explanation/audit/provenance
→ recover or reconcile after interruption/failure
```

The same supported workflow must remain usable with no AI provider. Agent assistance may improve interpretation and interaction, but it must remain upstream of authoritative intent, policy, approval and execution.

## Interaction model — many interfaces, one machine model

v0.10 makes Linura's **one model, many interfaces** principle observable as a complete workstation contract. Product breadth does not create additional authority paths.

| Interaction/product surface | v0.10 requirement |
| --- | --- |
| Intent/state-centric | Durable typed intent, desired state, authoritative observation and verified convergence remain canonical. |
| Control-plane-centric | Every Linura-managed external mutation uses trusted registered semantics and the appropriate Control lifecycle regardless of requesting interface. |
| Agent/conversational | Model input remains proposal-only and optional. |
| Manual/no-AI | Supported workflows remain complete through deterministic local interfaces. |
| Library/Setups/Profiles | Reusable local definitions are normal workstation workflows. |
| GUI Control Center | Supported graphical management client with CLI/protocol parity. |
| Configuration-centric | Versioned declarative configuration is typed, validated, previewable and non-authorizing. |
| Keyboard-centric | Supported workflows have keyboard navigation and essential shortcuts. |
| Command palette | Keyboard-first discovery/invocation of registered typed actions, intents, setups and navigation targets. |
| Quick settings | Supported workstation state uses authoritative observation and normal Control authority. |
| Shell/panel/tray/status | Linura owns the qualified first-party workstation chrome and status/entry-point experience. |
| Launcher/workspace UX | Application/action discovery plus session/workspace navigation are available as part of the workstation experience. |
| Notifications/OSD | Progress and outcome feedback reflects authoritative lifecycle state and verification. |
| Lock/session controls | Lock, logout and supported power/session actions are coherent, typed where authoritative, and recovery-safe. |
| Network/Bluetooth/audio/media | Required reference-profile controls use authoritative providers and trusted operation classes. |
| Display/power/storage | Required display, brightness, power and removable-storage workflows are explicit supported surfaces. |
| Desktop utilities | Screenshot/recording, clipboard/history and essential media/desktop integration are supported workflows. |
| Applications/packages | Application discovery and supported install/remove/default-app/package workflows are bounded and typed. |
| Updates/snapshots/recovery | Coordinated update, snapshot and recovery workflows are first-class end-user surfaces. |
| Personalization | Themes, wallpaper, fonts/icons and supported preferences use shared Linura contracts rather than ad-hoc mutation. |
| Install/First Boot | At least one exact bounded installer lane reaches owner enrollment on the qualified profile. |
| Unified visual/theme system | First Boot, installer, Control Center and shell surfaces share Linura design tokens and the first-party QML component SDK. |
| Keyboard/mouse/accessibility | Every supported workflow has keyboard/pointer parity plus required semantic accessibility and display-scaling evidence. |

The convergence rule is:

```text
intent / config / GUI / keyboard / palette / quick settings / CLI / agent
                                  │
                                  ▼
                       typed Linura state/actions
                                  │
                                  ▼
                           Linura Control
                                  │
                                  ▼
                        verified machine state
```

Configuration files, shortcuts and desktop controls are **input surfaces, not authority surfaces**. A declarative file may not contain arbitrary shell, executor permits, approvals or policy overrides. A shortcut/palette item may invoke only a registered typed operation or non-authoritative navigation action.

The UX remains proportional to trusted semantics and risk. Low-risk supported actions may auto-authorize under policy and feel immediate; higher-risk actions may require plan review or approval. UI ceremony may differ, but authority semantics may not.

Before execution, the registered typed operation is classified as `ExperienceEphemeral`, `AuthoritativeQuery`, `LinuraOwnedState`, `TransientExternalEffect`, or `ManagedExternalEffect`. Ephemeral navigation does not need a fabricated durable transaction. Transient external effects remain limited to the qualified unprivileged at-most-`UserState` envelope with Control mediation, authoritative preconditions, verification and audit. Privileged, stronger-risk, durable desired-state or ambiguity-sensitive effects use the full managed lifecycle or remain unsupported.

v0.10 requires a **complete first-party workstation shell experience** for the declared reference scope. Hyprland remains the compositor and upstream components may remain implementation dependencies, but panel/status/tray, lock/session, notifications/OSD and the other ordinary surfaces named by the release contract may not be deferred to post-v1 simply because an upstream substitute exists.

## Platform support boundary

The target profile is `profiles/arch-hyprland-v1.toml`:

- distribution: Arch Linux;
- init/service manager: systemd;
- session: Wayland;
- compositor: Hyprland;
- networking: NetworkManager;
- Bluetooth: BlueZ;
- audio: PipeWire + WirePlumber;
- storage integration: UDisks2;
- authorization integration: polkit;
- filesystem/recovery baseline: Btrfs + Snapper;
- inbound firewall default deny;
- SSH initially disabled;
- untrusted package sources disabled.

`arch-hyprland-v1` remains `development` until the v0.10 qualification dossier is satisfied and protected release closure updates the machine-readable support boundary. Merely landing code, UI or profile configuration does not make it supported.

v0.10 does **not** claim:

- arbitrary Arch installations;
- other Arch compositors/desktops;
- Ubuntu desktop support;
- Fedora, Debian, NixOS or other distributions;
- every GPU/driver/display topology;
- generic dual-boot, RAID, arbitrary partitioning/storage-layout or every-firmware installer support beyond the exact qualified v0.10 installer lane;
- unrestricted package, shell or vendor-script execution;
- remote/fleet control as part of the local workstation support claim;
- Stable/production support.

## Reproducible workstation qualification

Arch is rolling, so qualification may not depend on an unpinned `latest` repository or ISO. Before a release candidate can be accepted, the v0.10 qualification manifest must freeze:

- exact Arch installation/base-image identity;
- exact package repository snapshot or equivalent immutable package-set identity;
- exact package versions relevant to the profile contract;
- kernel, systemd, Hyprland, Mesa/driver and user-session identities used by qualification;
- exact Linura source/binary identities;
- exact virtual and physical hardware evidence identities.

A different package snapshot or materially different hardware lane is separate evidence, not automatic inheritance of the release claim.

## Two-layer evidence model

v0.10 requires both deterministic disposable-system evidence and workstation evidence.

### Layer A — deterministic disposable qualification

A reproducible Arch/systemd test environment proves installation/adoption, persistence, policy, update, recovery, migration and supported typed effects under fault injection. This lane may use virtualization where appropriate, but it may not claim real display/GPU/workstation behavior that the virtual environment did not exercise.

### Layer B — interactive workstation qualification

At least one explicitly identified maintained workstation lane must exercise the actual Wayland/Hyprland session and the supported workstation-facing capabilities. Before `arch-hyprland-v1` can enter `machine_classes.workstation.release_qualified_profiles`, release evidence must identify the exact hardware/driver/display lane or lanes that were actually qualified.

Unsupported GPU/driver/display/hardware combinations must fail closed or be reported as outside the release-qualified boundary rather than silently inheriting support.

## First Boot and adoption

v0.10 inherits the v0.9 First Boot authority boundary and adapts it to the workstation profile.

Supported workstation adoption must include:

- exact profile/environment discovery before support is claimed;
- interactive owner enrollment;
- durable restart-safe provisioning state;
- default/Library/import source handling with fresh authoritative observation;
- deterministic fresh plan derivation;
- verified recovery readiness before declaring the workstation ready;
- explicit unsupported-profile diagnostics;
- native CLI/recovery escape hatch independent of the graphical client.

v0.10 requires at least one bounded installer path that constructs or adopts the exact supported `arch-hyprland-v1` workstation, satisfies its disk-encryption/security contract, reaches owner enrollment and proves restart/recovery semantics. That requirement does not imply generic dual-boot, RAID, arbitrary custom partitioning or every-firmware support.

## Linura Control Center activation

v0.10 activates Linura Control Center as the first supported graphical management client for the qualified workstation profile.

Control Center is an **unprivileged protocol client**. It must not:

- hold a privileged executor handle;
- embed distro-specific mutation logic that bypasses providers/executors;
- create policy approvals on behalf of an unauthorized actor;
- turn model output directly into executable authority;
- trust executor self-reporting as final state;
- bypass durable lifecycle/recovery semantics.

Its supported responsibilities are to present authoritative observation, user intent/proposals, deterministic plans, policy/risk/approval state, execution progress, verification outcome, Library objects, diagnostics, audit/provenance and recovery/reconciliation guidance.

A CLI-equivalent path must exist for the supported authoritative operations so the system remains usable if Control Center is unavailable.

## Agent-assisted interaction

The v0.8 proposal boundary remains unchanged:

```text
human language / agent input
→ IntentProposal
→ deterministic validation / user review
→ authoritative typed intent
→ canonical lifecycle
```

The model may not own approval, policy, executor or recovery authority. Provider absence, provider failure or ambiguous interpretation must degrade to deterministic manual operation rather than weakening controls.

## Workstation capability slice

v0.10 should qualify only capabilities required for a meaningful workstation experience and only where Linura has typed providers/executors/verifiers with complete authority semantics.

The minimum target domains are:

- service/process lifecycle needed by the workstation stack;
- network observation and explicitly qualified NetworkManager state changes;
- Bluetooth observation and bounded BlueZ operations where implemented;
- audio/session observation and bounded PipeWire/WirePlumber operations where implemented;
- storage/removable-media observation and bounded UDisks2 operations where implemented;
- display/session/Hyprland observation required for workstation health and diagnostics;
- package/update behavior needed to keep the qualified Linura/profile stack coherent;
- Btrfs/Snapper recovery integration required by the profile contract.

A domain that lacks a narrow typed executor, independent verifier and adversarial qualification remains read-only or unsupported. v0.10 must not introduce a generic root shell to fill domain gaps.

## Library and setup experience

The local Linura Library becomes part of the normal workstation experience. A user must be able to:

- inspect exact Setup/MachineProfile revisions;
- create/save/adopt supported local configuration definitions;
- preview deterministic impact before adoption;
- import/export portable definitions with integrity/version checks;
- understand causal ownership and removal impact;
- recover after interruption without replaying historical approvals or effects.

Portable definitions remain declarative data, not executable scripts or authority tokens.

## Update, migration and recovery

v0.10 workstation qualification must cover:

- Linura update across the supported v0.9 → v0.10 persistent-state path;
- profile/package update interruption and deterministic reconciliation;
- reboot/power-loss across prepared/effect-started/commit windows for supported `ManagedExternalEffect` workstation mutations, plus bounded restart/re-observation evidence appropriate to any claimed `TransientExternalEffect`;
- Btrfs/Snapper recovery semantics where the profile claims them;
- recovery with Control Center unavailable;
- recovery with model/network unavailable where local recovery material exists;
- corrupted/newer persistent state fail-closed behavior;
- independent verification after recovery before normal mutation resumes.

A visually functional desktop with unproven recovery is not sufficient release evidence.

## Security boundary

The v0.10 workstation must preserve or strengthen the v0.9 baseline:

- default-deny inbound exposure;
- SSH disabled unless explicitly enabled through supported typed intent;
- no untrusted package sources;
- explicit polkit/authorization boundaries;
- no generic privileged shell endpoint;
- no client-held executor authority;
- exact actor/plan/evidence bindings;
- independent post-effect observation;
- fail-closed stale/substituted evidence handling;
- secret-bearing material excluded from ordinary proposal/audit diagnostics.

The interactive GUI must not become a broader authority surface than the deterministic CLI/protocol it represents.

## Qualification and failure matrix

The v0.10 candidate must exercise common failure semantics for every supported effect path:

- success;
- policy denial where policy applies;
- stale or invalid authoritative preconditions;
- unsupported profile/hardware;
- executor/effect failure;
- verifier failure;
- duplicate/replayed request where stable request identity applies;
- Control Center disconnect/restart;
- model/provider unavailable;
- offline operation where the capability does not inherently require network.

Every supported `ManagedExternalEffect` must additionally exercise no-change/idempotent convergence, approval required/expired/revoked where applicable, stale plan, indeterminate effect outcome, crash/restart before dispatch, crash/restart after effect start, crash/restart around durable commit, and recovery/reconciliation.

Every claimed `TransientExternalEffect` must instead prove bounded failure, fresh post-failure re-observation, no privileged execution, no durable desired-state obligation, and that any condition requiring durable ambiguity recovery promotes the operation to `ManagedExternalEffect` or unsupported.

## Required implementation workstreams

The authoritative detailed sequence is the 32-slice ledger in `contracts/v010-workstation-slices.toml`. At milestone level those slices group into:

1. **Contracts and authority foundation** — profile qualification, discovery, operation classification/registry, managed/transient Control paths and exact-source runtime qualification.
2. **Core first-party shell** — Control Center, UI SDK, command palette, workspace/application launcher, quick settings, lifecycle notifications/OSD, panel/status/tray and lock/session controls.
3. **Reference workstation domains** — network, Bluetooth, audio/media, display/brightness/power and required removable-storage workflows using authoritative providers and trusted typed effects.
4. **Daily-use workstation experience** — desktop utilities, application/package/default-app management, coordinated updates/snapshots/recovery and coherent personalization.
5. **Linura interaction convergence** — Library/Setups/MachineProfiles, declarative configuration, deterministic manual operation, proposal-only agent assistance, diagnostics/explanation/audit and shared visual semantics.
6. **Installation and onboarding** — bounded supported installer lane plus First Boot/owner enrollment/recovery readiness for the exact profile.
7. **Experience and hardware qualification** — artifact-bound visual/accessibility/input evidence plus a maintained real Arch/Hyprland hardware lane.
8. **Release closure** — fault/power-loss/security qualification, inherited v0.4–v0.9 gates, exact-source CI/Security/CodeQL and protected proof-first publication.

Completed slices require merged-PR evidence in the slice ledger. Planned slices carry no completion evidence. The completed set must remain a contiguous prefix and the ledger names exactly one next slice.

## Release gate

v0.10.0 is not release-ready until all of the following are proven:

- [ ] `arch-hyprland-v1` exact support identity, package set and maintained hardware evidence are frozen;
- [ ] all 32 entries in `contracts/v010-workstation-slices.toml` are complete with reviewable implementation/evidence lineage;
- [ ] the profile remains isolated from core distro-specific conditionals;
- [ ] at least one bounded supported install path satisfies the profile's encryption/security contract, reaches First Boot/owner enrollment, survives interruption and rejects unsupported substitutions;
- [ ] Control Center is an unprivileged typed client and supported authoritative operations have deterministic CLI/protocol parity;
- [ ] versioned declarative configuration is typed, validated, previewable, non-authorizing and has no arbitrary-shell/approval/policy bypass;
- [ ] every supported registered operation has trusted `OperationClass` semantics consistent across clients; unknown/ambiguous effects fail closed and no caller/provider/model can downgrade the class;
- [ ] every claimed `TransientExternalEffect` remains unprivileged and at most `UserState`, with Control mediation, authoritative preconditions, independent verification and audit;
- [ ] the complete first-party shell provides panel/status/tray, launcher/workspace, command palette, quick settings, lifecycle notifications/OSD and lock/session workflows without a parallel authority plane;
- [ ] required network, Bluetooth, audio/media, display/brightness/power and removable-storage workflows use authoritative state and typed effects;
- [ ] desktop utilities, application/package/default-app management, update/snapshot/recovery and personalization workflows meet the declared v0.10 contract;
- [ ] First Boot, installer, Control Center and supported shell surfaces use the shared Linura visual/theme foundation;
- [ ] every supported v0.10 end-user workflow has keyboard/pointer parity plus required accessibility/reduced-motion/scaling evidence or an explicit release-contract exception;
- [ ] the complete end-user intent → review → authorized effect → independent verification → audit loop works without AI;
- [ ] optional agent interpretation remains proposal-only and fail-closed;
- [ ] supported Library/setup/profile workflows are durable, versioned and recovery-safe;
- [ ] every supported `ManagedExternalEffect` workstation mutation has narrow typed authority, durable prepare/recovery and independent verification; claimed `TransientExternalEffect` operations satisfy their separate bounded no-durable-prepare contract;
- [ ] success, denial, stale evidence, executor/verifier failure, indeterminate outcome, restart and reconciliation are qualified;
- [ ] workstation update/migration/recovery and Btrfs/Snapper claims are exercised where declared;
- [ ] unsupported hardware/platform/install combinations are visible and fail closed;
- [ ] deterministic disposable-system qualification passes;
- [ ] explicit interactive workstation/hardware qualification passes;
- [ ] inherited v0.4–v0.9 mandatory qualifications remain green;
- [ ] exact-source CI, Security and CodeQL pass;
- [ ] release review freezes the exact Experimental support claim;
- [ ] Trusted Release Proof and independent published-release verification pass;
- [ ] only protected post-release closure marks `arch-hyprland-v1` release-qualified in the support matrix.

Until that gate closes, `arch-hyprland-v1` remains a development profile and v0.9's Ubuntu QualificationEnvironment remains the latest release-qualified machine environment.
