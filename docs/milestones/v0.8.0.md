# v0.8.0 — agent interpretation / IntentProposal

**Status:** implementation qualified; release-readiness finalization complete; terminal publication evidence remains controlled by the protected release lifecycle
**Claim class:** Experimental

## Purpose

v0.8.0 introduces model- and agent-assisted interpretation at a deliberately non-authoritative boundary. Natural-language, conversational and agent-originated input may be transformed into a typed `IntentProposal`, but no model output is executable and no provider receives policy, approval or executor authority.

The milestone builds on the released v0.7 durable intent/Library layer and the v0.6 managed-mutation lifecycle. It must preserve both boundaries rather than creating a parallel agent execution path.

## Implementation architecture

ADR [0028 — Proposal-only agent interpretation](../adr/0028-proposal-only-agent-interpretation.md) is the normative implementation decision for this milestone. It fixes ownership as follows:

- `linura-intent` owns the versioned proposal envelope, deterministic validation and canonical digest semantics;
- `linura-agent-runtime` owns bounded single-attempt interpretation execution, manual/no-provider interpretation and separately attributed per-attempt advisory results over an already-minimized Control-produced projection; it does not own cross-provider discovery/selection/scheduling, aggregate deadlines/budgets, retry/fallback admission, caching/coalescing, aggregation, secret minimization, acceptance authority, capability-registry authority or authoritative freshness;
- `linura-provider-sdk` owns the bounded credential-free `PreparedProviderInvocation`, provider-neutral interpretation adapter/invocation-gate ports and capability/network declarations, never policy, orchestration or execution authority;
- Linura Control owns provider discovery/eligibility, cross-provider selection/scheduling, aggregate deadlines/budgets, timeout/cancellation policy, retry/fallback/advisor admission, caching/coalescing and aggregation, plus trusted projection construction/minimization, authenticated-principal binding, current authority-context derivation, time-based observation-freshness revalidation, local capability-registry resolution, the applicable exact-bound human/policy acceptance decision, durable acceptance serialization, monotonic trusted-time authority-validity evaluation and acceptance orchestration;
- the Linura Library durable path owns atomic storage of the accepted intent and exact acceptance record, but its proposal-acceptance primitive is authority-internal, requires a sealed Control-minted commit capability rather than a public constructible request, and mechanically enforces the sealed trusted-time floor plus authority-validity deadline at durable linearization;
- provider-specific request encoding, response decoding, stream parsing and model APIs remain adapter-specific, while reusable credentials and side-effecting network/process/session transport remain private to the trusted permit-consuming invocation gate outside the untrusted runtime/adapter sandbox;
- proposal acceptance is a separate deterministic trusted boundary and cannot itself produce machine-mutation approval, dispatch or executor authority.

The v0.8 implementation must therefore be independently useful without a hosted provider and independently qualifiable with deterministic mock/replay providers.

## Core contract: IntentProposal

`IntentProposal` is an untrusted, typed proposal artifact suitable for deterministic validation and human/policy review. Its minimum contract should carry:

- schema/version identity;
- stable proposal identity and creation provenance;
- actor provenance that is never treated as authenticated-principal authority;
- normalized requested outcome;
- typed proposed requirements/constraints;
- assumptions and unresolved questions;
- uncertainty/confidence information where the provider supplies it;
- source/context references with bounded provenance;
- a Linura Control-minted authority-context revision plus canonical semantic-input digest;
- provider/model/adapter identity without embedding provider secrets;
- optional explanation/rationale as non-authoritative evidence;
- explicit capability references rather than executable commands;
- deterministic canonical representation suitable for hashing, audit and replay.

A proposal is never authentication, authorization, approval, policy decision, execution plan, transaction, capability grant or desired-state commitment merely because a model emitted it.

## Provider-neutral interpretation boundary

The interpretation layer must support adapters behind one stable proposal contract. Initial architecture must permit:

- local/offline providers;
- hosted API providers;
- enterprise-managed providers;
- deterministic mock/replay providers for qualification;
- complete manual operation when no model provider is configured or available.

Provider-specific protocol adaptation stays outside the canonical intent/authority model, but untrusted runtime/adapter logic receives no ambient provider egress, raw/reusable credentials or transport handles. It first produces a bounded credential-free `PreparedProviderInvocation`; Control validates the selected provider/adapter/endpoint and attempt bounds and binds the exact prepared-invocation digest. For each admitted attempt, Control mints an unforgeable single-use `ProviderInvocationPermit` exact-bound to that digest plus the canonical interpretation request, network/offline classification, per-attempt bounds and aggregate orchestration state. Only the trusted invocation gate receives and atomically consumes that permit before credential resolution, authentication, DNS, socket, process/session or provider transport initialization. It carries only the exact bound invocation. One permit authorizes at most one side-effecting provider call and is spent on every terminal outcome; automatic client retries, request-producing redirects/authentication replay, uncertain-write replay and stream reconnect/resume are disabled. Timeout, rate-limit, transport-failure, cancellation or partial-response outcomes return to Control without an internal retry, reissue or replacement/resume request; every repeated provider invocation requires a fresh Control admission and permit against the original aggregate budget/deadline.

Linura Control owns provider eligibility/discovery, selection, cross-adapter scheduling, aggregate deadlines/budgets, retry/fallback/advisor admission, caching/coalescing and aggregation. The runtime receives only a Control-admitted bounded attempt for one selected adapter and cannot autonomously select, retry, fallback or aggregate providers. Linura Control must construct the bounded data-minimized semantic projection before that projection crosses into the agent runtime. Raw secret-bearing Library, observation, retrieval or user context must not be handed to the runtime for it to filter itself. Control excludes secret values, privileged tokens, authority credentials and protected secret-bearing fields; where a secret dependency matters semantically, only a protected reference/handle or deliberately non-secret metadata may cross the runtime/provider boundary.

Offline mode is a hard network-isolation contract: a registered or selected network-required adapter must be rejected before adapter invocation or transport initialization, and provider discovery, selection, health-check, fallback, authentication, DNS or socket setup must not trigger network activity while offline mode is active.

## Deterministic promotion into authoritative intent

A model proposal may enter authoritative Linura state only through an explicit deterministic Linura Control-owned acceptance boundary:

1. parse and schema-validate the proposal and verify its canonical digest;
2. obtain the authenticated `Principal` from the trusted transport/session boundary independently of proposal fields;
3. validate actor provenance without treating actor equality as authentication or authorization;
4. re-read or re-resolve every authority-bearing observation, policy, Library object, capability-registry entry and relevant existing-intent dependency;
5. re-check time-based authoritative observation freshness using trusted Control time, reacquiring authoritative observations where required freshness expired and failing closed when fresh evidence cannot be established;
6. derive the current authority-context binding from that fresh/current material and require an exact match with the proposal binding;
7. resolve every capability/type against the current Control-owned local registry and reject unavailable, unknown, malformed, contradictory or unsupported references fail-closed;
8. surface assumptions, uncertainty and material transformations;
9. require the applicable Control-owned human/policy acceptance decision and prove that it is exact-bound to authenticated principal + proposal ID/digest + accepted Control context + durable operation identity + create/revise action + exact target identity/revision expectation;
10. acquire the authority-internal durable acceptance transaction/write-CAS guard before the final authority check;
11. while that durable guard is held, revalidate the complete authority/context/freshness/capability/decision binding using monotonic fail-closed trusted Control time, normalize every time-limited authority contributor to its exclusive first-invalid instant, derive the earliest required authority-validity deadline, capture the final-revalidation trusted-time sample as the sealed authority-time floor, and fail closed on authority-generation, target-revision, freshness, decision drift or expiry;
12. mint a transaction-scoped sealed exact-bound acceptance-commit capability carrying both the authority-time floor and authority-validity deadline;
13. consume it through the authority-internal Library acceptance primitive without releasing/reacquiring the guard, re-sampling trusted Control time at the actual intent+acceptance-record write/CAS linearization and rolling back unless `time_floor <= now < deadline`; any backward/reset/continuity-unknown sample fails closed and cannot revive expired authority;
14. atomically persist the resulting normal typed `Intent` in `Proposed` state together with the exact decision/proposal acceptance record;
15. make exact acceptance retry return the same durable result and reject semantic substitution/conflicting reuse; and
16. route any later machine mutation through the existing v0.6 observe/plan/validate/authorize/prepare/execute/verify/commit/audit/reconcile lifecycle.

The authority-internal Library acceptance primitive is not exposed as a public `LocalLibrary`/SDK mutation accepting caller-constructible authority fields. Its sealed commit capability must be non-user-constructible and non-deserializable from client/provider input, exact-bound to the final Control validation and durable transaction, carry the sealed trusted-time floor and earliest required authority-validity deadline, and be consumed for one durable linearization attempt. Calling the pre-v0.8 public `LocalLibrary::create_intent` operation alone is not sufficient evidence that a proposal was authenticated, authorized or exactly accepted.

## Staleness and provenance

Proposals are bound to a Linura Control-minted authority context. Qualification must cover stale observations, changed policy, changed Library objects, changed capability registries and superseded user intent between proposal generation and acceptance.

Reproducing an old caller-supplied revision or digest is not sufficient freshness evidence. At acceptance, Linura Control must derive the relevant current authority material again and also evaluate time-based observation freshness independently of revision equality. If a required observation validity window has expired without a revision change, Control must reacquire authoritative observation or fail closed. Where material semantic inputs are stale, Linura must require revalidation/re-proposal or a new explicitly reviewed proposal; it must not silently reinterpret stale text against newer authority-bearing state.

The durable write/CAS guard must be acquired before final authority-validity validation. Linura Control derives the earliest deadline across all time-limited authority inputs, including observation freshness and human/policy decision or approval applicability, and captures the final trusted-time sample as a sealed lower bound. Both values are carried into the sealed commit capability and enforced again at the actual durable write/CAS linearization, so a database-lock, scheduling or internal-I/O delay after capability minting cannot turn previously valid evidence or authorization into committed stale/unauthorized acceptance. If the deadline is reached/passed, or trusted Control time moves backward below the sealed floor or loses monotonic continuity, the transaction aborts and the caller must re-enter Linura Control for fresh authority establishment.

Immediately before durable acceptance, Linura Control must revalidate under that durable acceptance serialization boundary so a concurrent policy, capability-registry, Library, existing-intent, target-revision or observation change cannot race between a successful review and the commit. The durable acceptance record preserves exact acceptance-decision/proposal-to-intent provenance plus the sealed trusted-time floor and authority-validity deadline enforced at linearization, so a lost response or process restart cannot produce a duplicate intent, replay an authorization decision over substituted or expired material, revive stale authority through clock rollback, or lose the model-derived lineage.

## Adversarial-input boundary

Prompt injection and malicious content are expected inputs, not exceptional states. The proposal layer must treat as untrusted:

- user-provided text;
- retrieved documents/web content;
- provider-generated tool/action suggestions;
- model-produced structured payloads;
- quoted instructions embedded in data;
- cross-provider or specialist-agent recommendations;
- actor, context, capability and authorization claims embedded in proposal data.

The model, agent runtime or client cannot authenticate a principal, grant itself tools, expand the local capability registry, mint/advance the authoritative context revision, choose its own approval level, suppress required warnings or manufacture trusted provenance.

## Multi-advisor and disagreement semantics

If multiple providers/specialists are supported, disagreement must be represented explicitly rather than averaged into hidden authority. Linura Control owns the cross-advisor schedule and deterministic rule used to select, combine or reject proposal/advice records; the runtime cannot initiate or aggregate additional advisors on its own. The system preserves each proposal/advice source and material conflict.

Consensus between models is not authorization.

## Privacy and secrets

Linura Control owns provider/runtime projection construction and data minimization. Secret values, privileged tokens, authority-bearing credentials and protected secret-bearing Library/observation/retrieval/user fields are removed before the projection crosses into the agent runtime. Only protected references/handles or intentionally non-secret projections may be sent when needed for interpretation.

Redaction/data-minimization behavior must be deterministic and testable before runtime invocation, including hosted-adapter paths. Provider/runtime failures, diagnostics, prompts and audit surfaces must not leak secret-bearing source context or arbitrary provider response bodies.

## Required qualification

v0.8 qualification must cover at minimum:

- deterministic `IntentProposal` schema/canonicalization and version rejection;
- provider adapter conformance across deterministic mock/local and hosted-style transports;
- Control-owned provider discovery/selection/scheduling, aggregate deadline/budget, retry/fallback/advisor, caching/coalescing and aggregation policy, including negative evidence that the runtime cannot self-select another adapter, self-retry, self-fallback, reset aggregate budgets or aggregate advisors, and production-equivalent isolation evidence that malicious adapter logic cannot obtain provider credentials/direct egress or repeat an invocation without a fresh single-use Control permit;
- offline pre-invocation rejection of a registered/selected network-required adapter with zero adapter callback, transport-init, DNS/socket/authentication activity;
- malformed/partial/oversized/unknown-field output rejection;
- prompt-injection and malicious tool/action proposal handling;
- Control-owned secret-bearing semantic-context minimization before agent-runtime invocation and no leakage through diagnostics/audit;
- caller/agent actor spoofing cannot substitute for authenticated `Principal` identity or acceptance authorization;
- acceptance authorization is exact-bound to proposal digest, accepted context, operation identity, create/revise action and target identity/revision, and cannot be replayed over substituted material;
- stale observation/context/policy/Library/capability references, including replay of an internally consistent old binding;
- expiry of time-based observation freshness without a revision change is detected and requires fresh authoritative observation or fails closed;
- post-mint expiry of any sealed time-limited authority—including observation freshness and decision/approval applicability—caused by database-lock/scheduling/internal-I/O delay is detected at durable write/CAS linearization and aborts without intent or acceptance-record mutation;
- post-mint trusted-Control clock rollback below the sealed time floor is detected at durable write/CAS linearization and cannot revive stale observation or expired decision/approval authority;
- capability references are resolved only against the current Control-owned registry and providers/clients cannot expand it;
- provider timeout, cancellation, rate-limit, malformed-stream and unavailability behavior;
- manual/no-provider operation without weakening trusted acceptance checks;
- final authority revalidation is serialized with the durable acceptance linearization point and concurrent authority drift fails closed;
- direct public Library/SDK calls cannot fabricate or bypass the sealed Control-minted acceptance capability;
- atomic proposal acceptance idempotency across lost response/restart and exact acceptance-decision/proposal→intent lineage preservation;
- proposal-ID/operation-ID/decision-ID semantic substitution and conflicting principal/context/target/intent reuse fail closed;
- explicit assumptions/uncertainty/provenance preservation;
- multi-advisor disagreement/conflict representation if that surface ships;
- proof that proposal acceptance creates typed intent but does not create machine-mutation approval/executor authority;
- inherited v0.7 persistence/Library and v0.6 managed-mutation qualifications;
- exact-source CI, Security and CodeQL;
- release proof, reproduction, immutable publication and independent verification.

## Release gate

v0.8.0 is not releaseable until:

- [x] implementation matches this proposal-only capability boundary;
- [x] `IntentProposal` schema, provenance, staleness and deterministic validation contracts are complete;
- [x] Linura Control constructs/minimizes semantic context before the agent runtime and secret-bearing raw context never crosses that boundary;
- [x] authenticated-principal binding and applicable exact-bound Control-owned acceptance authorization are qualified independently of proposal actor fields;
- [x] current authority-context and capability-registry resolution are Control-owned, time-based observation freshness is revalidated at acceptance, and stale/substituted caller state fails closed;
- [x] the durable acceptance guard is acquired before final revalidation, the sealed capability carries both the final-revalidation trusted-time floor and earliest required authority-validity deadline across observation freshness and decision/approval applicability, and actual write/CAS linearization rejects deadline expiry and trusted-time rollback rather than committing stale or unauthorized acceptance;
- [x] final acceptance revalidation is serialized with the durable linearization point and concurrent authority drift cannot commit stale authorization;
- [x] the authority-internal Library acceptance primitive requires a sealed non-public Control-minted commit capability and direct public SDK/Library calls cannot bypass it;
- [x] provider-neutral adapter and no-provider/manual paths are qualified, including Control-owned cross-provider orchestration, negative runtime self-orchestration tests, single-use invocation-gate/direct-egress containment and adapter-internal retry-escape tests, and pre-invocation offline rejection of network-required adapters;
- [x] adversarial prompt/tool proposal and malformed-provider-output cases fail closed;
- [x] atomic exact acceptance-decision/proposal-to-intent idempotency/provenance survives lost response and restart;
- [x] proposal acceptance is proven unable to manufacture policy, machine-mutation approval or executor authority;
- [x] inherited v0.6/v0.7 authority, durability, Library and recovery qualifications remain green;
- [x] canonical source checks pass on the exact candidate;
- [x] dedicated v0.8 proposal/agent qualification passes on the exact candidate;
- [ ] Trusted Release Proof includes v0.8 qualification and succeeds;
- [ ] metadata-only release authorization preserves the reviewed implementation tree;
- [ ] tag-last publication succeeds;
- [ ] independent published-release verification succeeds;
- [ ] post-release closure advances machine roadmap state only after immutable publication evidence exists.

The terminal publication, independent-verification and closure criteria intentionally use the canonical closure vocabulary. Pre-publication implementation/qualification criteria must be completed before release readiness is declared.

## Explicit non-claims

v0.8.0 does not claim autonomous execution, unattended privileged agents, generic tool authority, policy-administrator authority, direct shell execution, a supported Linux distribution/machine profile, hosted Library synchronization, fleet control, Stable APIs or production readiness. Agent/model authority remains `proposal-only`.
