# ADR 0054 — S26 preserves Local Library authority across workstation workflows

- Status: Proposed
- Scope: v0.10 S26, `arch-hyprland-v1`, S16 predecessor; S27 consumes supported declarative configuration
- Reuses: released v0.7 Local Library, v0.8 secure proposal acceptance, accepted ADRs 0008/0017/0018/0028/0031/0032/0033, v0.9 migrations
- Companion: [inactive design](../../contracts/v010-s26-design.toml), [native qualification](../qualification/v0.10.0-s26.md), [security qualification](../qualification/v0.10.0-s26-security.md)
- ADR number is provisional to this independent WIP branch; reconcile with the append-only accepted ADR ledger at PR extraction.

## Context and decision

The released `linura-library` crate already provides `LocalLibrary`, schema v1 SQLite/WAL persistence, stable intent lifecycle, append-only Setup/MachineProfile revisions, exact references, causal ownership/removal-impact, deterministic integrity-bound portable Setup/Profile bundles, atomic local import/adoption, preflight, backup validation and restore. The native adoption implementation exposes `AdoptionContext` with available *secret references*, target machine class and unsupported capabilities; `AdoptionReport` records collisions, missing secret references, unsupported capabilities, creates/reuses and `requires_plan`. Those are **data-layer** operations; they do not execute an OS configuration.

**Decision:** Build the v0.10 workstation Library/Setups/MachineProfiles experience as an *authenticated, typed projection and editor of the existing released Local Library*. Do not introduce parallel SQLite catalogs, user-interface-owned object stores, a new portable format, a shadow ownership graph, or an approval/executor path. The accompanying S26 design is **inert**; no new runtime operation, UI controller or filesystem mutation is enabled, no status/qualification promoted.

### Four distinct meanings of "adoption"

1. **Open/select/compare** an immutable Library object/revision: bounded read-only observation or UI projection, not an effect.
2. **Import/adopt a portable bundle into Local Library**: existing `import_setup_bytes`, `import_profile_bytes` or `adopt_*_bundle` with `dry_run=false`, validated and stored in a local idempotent transaction. This is `LinuraOwnedState` only; it does not activate intents or apply changes on a host.
3. **Select/revise desired intent** for a target machine: an independently authenticated revisioned local lifecycle transition through the existing intent APIs and causal ownership constraints. A proposed draft is not accepted current desired state merely because imported.
4. **Apply a Setup/MachineProfile to the actual machine**: fresh target observation, current capability/PlatformProfile resolution, canonical planner/operation registry, trusted principal and policy, risk/approval, class-specific narrow execution, independent postcondition, audit and reconciliation. **Never implement this as one generic privileged `adopt-setup` executor.** Each native effect stays with its registered domain owner and managed/transient semantics. Historical import/acceptance records and operation IDs are not execution grants.

A `MachineProfile` expresses reusable machine composition; it is not `PlatformProfile` hardware/provider compatibility, a qualification environment, a Btrfs snapshot, or authenticated principal. A profile's machine-class hints or constraints do not guarantee that the target device, required capability or credential exists.

## Exact identity, revision and provenance

Bind authenticated local principal (not imported actor provenance), intended machine/boot/session where applicable, Library database instance and schema version, exact `SetupId` + `u32` revision, `ProfileId` + `u32` revision, `IntentId` + `u64` revision, canonical content digest, closure references, validated causal generation/completeness and current operation-id idempotency semantics. Names/descriptions/display order, bundle filenames, request IDs alone or displayed version badges are not authority identities. Reopen/fresh-read before local CAS/save, import, diff, preview or applying changes; stale revision must reject and offer a new draft instead of silently adopting another revision.

The existing `StoredSetup` contains immutable nested setup/intent revision references, and `StoredProfile` holds both profile revision and setup/intent revision references. Resolve a complete bounded dependency closure, reject cycles, duplicates with conflicting digests, missing revisions, inconsistent composite logical/revision references and ambiguous shared owners. Do not silently resolve a reference to the newest revision, guess a different revision or flatten an incomplete graph into actionable desired state.

The existing causal `RemovalImpactReport` differentiates `removable`, `retained_shared` and `indeterminate`. Only a complete owner projection can justify cleanup eligibility, never UI selection, a no-longer-visible card or the retirement of one of several owners. Shared resources remain managed while any independent owner continues to require them.

## Local revisions, portable format and source trust

Reuse `LocalLibrary::save_setup`, `save_profile`, current/history read methods, durable operation-ID semantics and SQLite transaction/foreign-key constraints. On collision or stale revision, reject *before* mutating rather than inventing a new ID or overwriting previous immutable history. A visual editor is a draft: explicit review/cancel/save must use current schema, exact references and authenticated local owner. Newer format/schema versions are unsupported until separately versioned migration; preserve old bytes and safe backup recovery. Do not weaken released `LIBRARY_SCHEMA_VERSION=1` or `PORTABLE_FORMAT_VERSION=1` on an S26 UI branch.

Portable bundles use existing deterministic `encode/decode_setup_bundle` and `encode/decode_profile_bundle`, bounded record/byte limits and SHA-256 integrity; they are **untrusted declarative data**. A digest detects accidental/malicious byte modification relative to a declared digest but is **not a signer identity, origin authentication or trust delegation**. Imported actor IDs, requirements, labels, portable constraints, machine class, file paths, recorded approvals or audit strings never become authenticated approval, principal, policy or executor handles. Only validated secret-reference *identifiers* can be stored or exported, never secret values or reuseable credentials. Missing references and incompatible target machine/capability must appear as explicit blockers, not silently provision secrets or switch implementation providers.

An export creates a new user-owned **external filesystem artifact** separate from Library reads; safe target descriptor, bounded content, digest, atomic publication and independent result are required. A backup likewise creates an independent protected database artifact. Restoring a backup replaces active Library state and may roll it backward: treat restoration as a **destructive managed external effect** with explicitly stopped/quiescent owners, verified schema/integrity, audited prior-state safeguard and safe atomic replacement. `restore_backup` exists, but its presence is not proof that a running authority daemon can swap the database safely. No permission to touch arbitrary directories/symlinks or delete a shared Library is inferred from a file chooser.

## Fresh machine impact and policy boundaries

Before claiming a supported *machine impact preview*, Control must obtain fresh authenticated local target state and capability/provider availability, selected PlatformProfile, all immutable desired revision closure, actual existing desired/observed resources, causal owners and constraints; derive a canonical `ReconciliationPlan` with original scope, operation-class registry, resource identities, policy revision and trusted risk floor. `AdoptionReport` is **not** that canonical execution plan; `requires_plan=true` must not be interpreted as “approved”. A dry-run against imported bundle context checks Library compatibility and local collisions only; it cannot predict every workstation resource or permission consequence.

Do not persist or replay plan authorizations, native executor receipts, historical approval references or `ProposalAcceptancePermit` as reusable permissions in a Setup/Profile or portable artifact. Trusted `Principal` comes from the active authority transport, `Actor` from provenance. No model, agent, UI, imported content or SDK can register an effect, pick a risk floor, force the executor or claim verified convergence.

External mutations must follow the existing domain-specific managed request → observe → plan → validate → authorize → prepare → execute → verify → commit → audit → reconcile path, or an already trusted and qualified bounded transient path. Applying a profile spanning NetworkManager, BlueZ, PipeWire, devices, packages and power is **not** one atomic OS transaction: track per-domain verified outcomes and irreversibility, retain indeterminate failures and reconcile without replay. A local Library commit succeeding does **not** establish native convergence. Likewise retaining a previous local revision is not proof that an OS change can be rolled back.

## UX, interoperability and qualification

The first-party Control Center, Library/Setups/MachineProfiles panels, CLI/SDK and no-model manual path must project the **same** live LocalLibrary/Control authority: browse/filter/history, immutable revision compare, editor/diff, nested graph and shared owner explanations, portable export/import staging, preflight blocker details, explicit Save/Cancel, selected target planning and verified adoption progress. Resolve language, keyboard/screen-reader/focus, reduced motion, scaling/HiDPI and source provenance in the compiled `org.linura.UI 1.0` SDK. ShellBridge is presentation/typed-client infrastructure only, not a second catalog or policy engine.

[Qualification](../qualification/v0.10.0-s26.md) and [adversarial security](../qualification/v0.10.0-s26-security.md) specialize v0.10 Q9–Q14 while preserving released v0.7/v0.8/v0.9 and S17/S21 protections. Exact-source SQLite/portable tests and VM UI qualification cannot by themselves claim physical Q11 machine effects. A proposed ADR, an inert contract or a UI screen is not implementation evidence. Extract future PRs adaptively by audited identity, persistence, machine-plan, native-effect and UI/evidence boundaries; no fixed PR count.
