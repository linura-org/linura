# ADR 0021: v0.5 qualifies an isolated executor and pure verifier before lifecycle integration

Status: Accepted

## Context

v0.4 established durable reviewed-authority preparation, pre-dispatch serialization, sealed process-local dispatch permission, indeterminate recovery and verified commit semantics without shipping an executor or claiming a supported managed external effect.

The next architectural risk is no longer persistence. It is the privileged boundary itself: whether a narrow effector can receive an exact operation, authenticate the operating-system caller, authorize that caller with an OS policy mechanism, dispatch one bounded native effect, and then remain unable to prove its own success.

Integrating such an effector directly into `linura-control` in the same milestone would collapse two questions into one and would make a qualification experiment look like supported managed mutation. v0.5 therefore needs a deliberately smaller claim.

## Decision

v0.5 qualifies one isolated systemd executor and one independent verifier under the following hard boundaries.

### Executor boundary

- The executor is a separate root-owned system D-Bus service, `org.linura.Executor.Systemd1`.
- Its only v0.5 operation is `RestartUnit` for canonical `linura-v05-qualification-*.service` fixtures.
- It has no arbitrary command, shell, path, package, file, unit-type or generic systemd method surface.
- The system-bus unique sender name is obtained from the authenticated D-Bus message header; caller identity is never accepted as a method argument.
- Authorization is a distinct Polkit decision for `org.linura.executor.systemd.qualify-restart`. The production policy does not grant the disposable-VM qualification user; that grant lives only under `tests/acceptance/v05/`.
- The supplied transaction/generation/digest binding is correlation and anti-substitution material, not bearer authority. A caller must still pass the OS authentication/authorization boundary.
- The executor validates the canonical fixture namespace, wire digests, effect digest and dispatch digest before native dispatch.
- Dispatch uses the native systemd D-Bus `RestartUnit(unit, "replace")` call. It never shells out to execute the requested effect.
- The only fixed external helper is `/usr/bin/pkcheck`, invoked with a fixed action identifier and the authenticated system-bus unique name.
- A successful systemd method acknowledgement is reported only as `dispatched`; it is not treated as machine-state success. Ambiguous native dispatch failure is `indeterminate`.

### Observation and verifier boundary

- `linura-linux-observation` remains the canonical owner of systemd machine truth and exposes `ActiveEnterTimestampMonotonic` in the authoritative `ObservationEnvelope`.
- The v0.5 verifier is pure: it owns no D-Bus connection, imports no concrete executor and acquires no native observation itself.
- Verification consumes only an expected restart postcondition plus a fresh canonical observation.
- Satisfied verification requires the exact provider/resource/capability identity, `NativeApi` authority, a current freshness window, matching unit identity, loaded/active state, and an activation timestamp strictly newer than the pre-dispatch baseline.
- Executor receipts, return strings and dispatch acknowledgements are structurally excluded from success proof.
- Stale, future, structurally mismatched or insufficient observations are `inconclusive`; authoritative contradictory state is `not-satisfied`.

### Product and lifecycle boundary

- v0.5 does not connect the executor to `linura-control`, the public SDK, protocol, CLI mutation surface, durable recovery authority or model/agent runtime.
- `managed_mutation_support` remains `none` and `complete_lifecycle` remains `false` for the v0.5 release claim.
- v0.6 is the first milestone permitted to integrate the qualified component with the complete canonical lifecycle and claim one supported managed external effect.

### Qualification boundary

A permanent disposable-VM workflow must run the exact source under real systemd, D-Bus and Polkit and prove at minimum:

1. an ordinary caller is denied;
2. wrong namespace and malformed/substituted binding fail before dispatch;
3. a nonexistent namespaced fixture yields conservative `indeterminate` dispatch classification;
4. the authorized test principal can dispatch only the fixed qualification restart;
5. canonical post-observation shows a strictly advanced activation timestamp;
6. the pure verifier returns `satisfied` for the fresh canonical post-state, `not-satisfied` for an unchanged restart baseline, and `inconclusive` for stale evidence;
7. the executor service retains its systemd hardening and empty capability sets;
8. exact-source evidence records the bounded claim and artifact hashes.

The qualification workflow is a mandatory Trusted Release Proof dependency for v0.5.

## Later integration

v0.6 preserves this ADR as the historical v0.5 qualification boundary and extends the executor with a separately bounded managed active-state operation for canonical `linura-managed-*.service` units. The v0.6 product path does **not** make the old qualification principal or `qualify-restart` action into product authority.

The complete v0.6 composition—`Authority1`, `linura-authorityd`, separate human and executor authorization, durable stable-operation binding, fresh independent active-state verification and no-blind-replay recovery—is defined by ADR 0025. This is a refinement of the component's use after v0.5; it does not retroactively change the v0.5 release claim that lifecycle integration was absent.

## Consequences

### Positive

- The first privileged component can be attacked and qualified without widening Linura's public authority surface.
- OS identity/authorization, dispatch correlation and postcondition verification remain separate trust decisions.
- A compromised or buggy executor cannot make its own acknowledgement count as current machine truth.
- The canonical observer remains the one systemd truth source instead of diverging into verifier-specific D-Bus logic.
- The disposable-VM protocol provides permanent negative evidence, not only a happy-path unit test.
- v0.6 can integrate a component whose narrow privileged boundary already has direct qualification evidence.

### Costs

- v0.5 intentionally exposes no useful general-purpose mutation feature to users.
- The qualification-specific D-Bus method, fixture namespace and test principal must be removed or explicitly superseded when the production lifecycle is introduced.
- A root service remains high consequence even with an empty Linux capability bounding set because root plus system D-Bus access can reach privileged systemd APIs; code, D-Bus policy, Polkit policy and service hardening therefore remain security-critical review surfaces.

## Rejected alternatives

### Integrate executor and Control in v0.5

Rejected. It would combine privileged-component qualification with lifecycle authority integration and prematurely widen the release claim.

### Let the executor verify its own effect

Rejected. Dispatch acknowledgement is not authoritative post-state and would create a self-attesting confused-deputy boundary.

### Give the verifier its own systemd D-Bus client

Rejected. That duplicates the canonical Linux observer and risks inconsistent identity, freshness and state semantics.

### Use a generic privileged shell or systemd proxy

Rejected. It would turn a bounded qualification component into arbitrary root command/systemd authority and make policy reasoning intractable.

### Treat digests as bearer authorization

Rejected. Deterministic bindings detect substitution and correlate decisions; they do not authenticate the operating-system caller or grant execution authority.
