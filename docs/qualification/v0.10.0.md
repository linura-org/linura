# v0.10.0 qualification — interactive Arch/Hyprland workstation

**Status:** planned; implementation and release evidence pending
**Claim class:** Experimental
**Target PlatformProfile:** `arch-hyprland-v1`

This dossier defines the evidence required before Linura may claim its first release-qualified interactive workstation PlatformProfile.

v0.9's Ubuntu 24.04/amd64/QEMU-TCG/headless lane remains an inherited **QualificationEnvironment**. It is not converted into a PlatformProfile by this milestone. v0.10 adds independent evidence for `arch-hyprland-v1`; passing the inherited Ubuntu lane alone is insufficient.

## Candidate identity contract

The candidate profile is:

- PlatformProfile ID: `arch-hyprland-v1`;
- machine class: `workstation`;
- distribution family: Arch Linux;
- init/service manager: systemd;
- session: Wayland;
- compositor: Hyprland;
- network provider: NetworkManager;
- Bluetooth provider: BlueZ;
- audio provider: PipeWire + WirePlumber;
- storage provider: UDisks2;
- authorization provider: polkit;
- filesystem/recovery baseline: Btrfs + Snapper.

Before release qualification, the evidence manifest must additionally freeze the exact Arch base/install source, immutable package snapshot or equivalent package-set identity, relevant package versions, kernel/session/graphics stack, exact Linura source/binaries and exact virtual/physical hardware evidence lanes.

`latest`, an unbounded rolling package set, or an unspecified hardware/driver combination is not a valid release evidence identity.

## Support-state transition

During implementation:

- `profiles/arch-hyprland-v1.toml` remains `status = "development"`;
- `hardware/support-matrix.json` keeps `machine_classes.workstation.release_qualified_profiles` unchanged;
- no UI, provider, executor or passing unit test may independently promote the profile to supported status.

Only protected post-release closure after immutable publication and independent verification may add `arch-hyprland-v1` to the release-qualified workstation lane.

## Q1 — source, profile and component contract

Required evidence:

- the target profile parses and validates under repository contracts;
- distro/compositor assumptions remain outside distribution-neutral core crates;
- exact provider/executor/verifier ownership is declared for every supported workstation effect;
- Linura Control Center is activated only when it is an unprivileged typed client;
- unsupported/planned components do not silently enter the release artifact/support claim;
- release artifacts derive from repository-owned component contracts;
- exact source SHA and profile revision are bound to qualification evidence.

Negative cases include malformed profile data, unknown provider identity, incompatible session/compositor, profile substitution and a component marked present without release activation evidence.

## Q2 — reproducible Arch substrate

A deterministic disposable qualification lane must prove that the candidate is built and exercised against a reproducible Arch package universe.

Required evidence includes:

- immutable base/install source identity;
- immutable package repository snapshot or equivalent exact package-set digest;
- exact installed versions for kernel, systemd, Hyprland, graphics/session dependencies and profile-critical providers;
- exact architecture and virtualization identity;
- exact candidate binary digests;
- rejection of substituted package snapshot/base source;
- no hidden dependency on mutable `latest` repositories during evidence production.

This lane proves deterministic system semantics but does not by itself prove real workstation graphics/hardware support.

## Q3 — workstation environment discovery and compatibility

Production discovery must construct live evidence and compare it against the candidate profile boundary without turning compatibility into a support claim. The typed assessment has exactly three outcomes: `ExactCandidateMatch`, `KnownMismatch`, or `InsufficientEvidence`. A known contradiction wins over incomplete evidence; otherwise any missing or ambiguous required fact yields `InsufficientEvidence`. Even `ExactCandidateMatch` remains candidate-only and cannot set release support.

For the current v0.10 candidate, positive identity evidence covers Arch, x86_64, systemd, Wayland, Hyprland, and the exact selected provider identities. Arch is rolling, so Ubuntu-style `VERSION_ID` is not a required PlatformProfile fact; exact package versions belong to the separately frozen Arch qualification substrate.

Production discovery is deliberately split across the canonical observation and Control boundaries. `linura-linux-observation` provides narrow bounded probes for distribution, architecture, init, one explicitly selected logind session/user, compositor, provider identity, audio and root filesystem. Each successful probe emits a canonical `ObservationEnvelope` with source-appropriate provenance such as filesystem, kernel/procfs, logind/native API, provider D-Bus health, user-systemd or Hyprland IPC. It does **not** aggregate those probes into a second observation model or a PlatformProfile decision.

The session-dependent probes accept a Control/composition-selected logind session identifier plus expected uid; they do not assume the collector process belongs to the target graphical session. Native file probes have explicit byte ceilings. D-Bus connection establishment/authentication and method calls are bounded; provider evidence requires the well-known service to be currently owned and to answer a direct bounded health probe, so an activatable-only name is insufficient. For the network role, liveness alone is not provider-selection evidence: NetworkManager must additionally report at least one managed non-loopback device through its native device API or the network-provider fact remains unavailable. PipeWire/WirePlumber evidence is bound to the selected logind user's runtime bus and user-systemd unit state. A positive Hyprland compositor fact derives candidate socket paths from the bounded kernel-owned Unix socket table rather than traversing the user runtime subtree, then requires kernel peer credentials from the connected Unix socket, the peer PID resolving through logind to the exact selected session object, and a bounded Hyprland version response over that same connection. Process-global environment hints and runtime-directory enumeration are not compositor identity or session-binding evidence.

`linura-control` owns capability de-duplication, cross-fact compatibility aggregation, mismatch precedence and the final tri-state outcome over the resulting canonical envelopes. `linura-hardware` contains only the provider-neutral candidate contract, result types and single-fact assessment rules. Missing, stale, future, wrong-provider or incomplete canonical evidence remains `InsufficientEvidence`; duplicate capability evidence fails closed; a known contradictory fact remains `KnownMismatch`. These facts establish only live candidate compatibility. They are not hardware-lane qualification, package-snapshot evidence, mutation authority, or support-promotion evidence; those remain independently bound by the rest of this dossier.

Negative evidence must cover at minimum:

- another distribution;
- another compositor or X11 session;
- non-systemd init;
- unsupported architecture;
- missing/incompatible required provider;
- unsupported filesystem/recovery baseline where the release claim requires it;
- substituted hardware/driver/display lane;
- incomplete or ambiguous live discovery.

Unsupported or ambiguous environments remain visible but do not acquire support status or mutation authority.

## Q5 — Control Center authority isolation

Linura Control Center must be tested as an unprivileged protocol client.

Required evidence:

- no client-held privileged executor handle;
- no client-side generic root command path;
- no distro-specific direct mutation bypassing Linura providers/executors;
- policy/approval state originates from authoritative services, not UI fabrication;
- model output cannot become execution authority in the client;
- displayed execution success is not final until authoritative verification completes;
- reconnect/restart reconstructs state from durable authoritative records;
- CLI/protocol parity exists for supported authoritative operations;
- Control Center failure does not remove native recovery access.

Adversarial client input must not widen protocol authority.

## Q6 — manual end-user lifecycle

With all model providers absent, an experimental user must be able to complete the supported lifecycle. For a supported `ManagedExternalEffect`, the qualified path is:

```text
observe
→ express/select typed intent
→ deterministic plan
→ review policy/risk/approval requirement
→ authorize where permitted
→ durable prepare
→ narrow execution
→ independent verification
→ commit/audit
→ reconcile if needed
```

A qualified `TransientExternalEffect` instead follows the machine-readable bounded transient lifecycle in `contracts/operation-semantics.toml`: `request → observe → plan → validate/classify → authorize → execute → verify → audit`. Its policy subject must derive from the exact canonical `ReconciliationPlan` plus authenticated principal. It has no durable prepare/commit/reconcile transaction and is supportable only while its bounded failure semantics do not require durable indeterminate recovery.

Required cases include:

- no-change/idempotent convergence;
- supported change success;
- deterministic preview;
- policy deny;
- approval required;
- expired/revoked approval;
- stale observation;
- stale plan;
- duplicate request;
- audit/explanation retrieval.

## Q9 — supported workstation capability domains

Every external effect included in the v0.10 release claim must first bind to the trusted operation-semantics contract in `contracts/operation-semantics.toml`.

For each supported `ManagedExternalEffect` domain, qualification must independently prove:

- typed normalized desired/effect state;
- authoritative observation;
- deterministic planning/diff;
- trusted operation/risk classification and policy/authorization binding;
- durable prepare/idempotency;
- narrow privileged executor where privilege is required;
- independent verifier;
- commit/audit/reconcile behavior;
- least-privilege authorization;
- no generic shell fallback.

A claimed `TransientExternalEffect` is a separate narrow support slice and must prove all of the following instead of pretending to be a managed mutation:

- registered typed operation descriptor with trusted `TransientExternalEffect` class;
- trusted risk no higher than `UserState`;
- no privileged executor or generic shell;
- Control mediation with authoritative current state/preconditions as required by the domain;
- deterministic canonical plan plus authenticated-principal policy binding, with no client/provider/model class downgrade;
- the same policy gate applies before a no-change success is returned or audited;
- bounded execution plus independent post-effect verification whose provider evidence timestamp is strictly later than Control's dispatch-start lower bound;
- audit/correlation sufficient to explain the transient operation;
- bounded failure semantics that do not require durable indeterminate recovery;
- automatic promotion to `ManagedExternalEffect` or unsupported when privilege, stronger risk, durable desired state, ambiguity/recovery or other managed semantics are required.

Candidate domains may include NetworkManager, BlueZ, PipeWire/WirePlumber, UDisks2, systemd lifecycle, package/update and Btrfs/Snapper integration. A domain may qualify query/transient/managed operations independently; one class does not inherit support from another.

### Current transient-effect implementation boundary

The repository now contains the first concrete implementation candidate for current-session PipeWire output volume on top of `linura_control::TransientEffectControl`: trusted exact operation registration, an authoritative WirePlumber ObjectManager observer, identity-bound unprivileged mixer execution, fresh post-effect re-observation, bounded durable SQLite audit, same-UID `Session1` transport, SDK/CLI parity, and a packaged root-owned helper. Those implementation pieces are reviewed as one authority slice; none of them independently promotes release support. The reusable transient Control substrate remains only a mechanism: **That substrate is not itself a supported external effect.**

`operation:audio.output.set-session-volume` remains **unpromoted/unsupported as a v0.10 release claim** until the release qualification retains the required real workstation evidence, including the maintained interactive Q11 lane with the packaged PipeWire/WirePlumber runtime and the applicable failure, timeout, restart and verification cases. Static contract checks, unit tests and synthetic observers/executors are necessary implementation evidence but cannot substitute for that hardware/session qualification. **Test-only operation descriptors and synthetic observers/executors are architecture qualification, not support activation.** Missing or stale interactive evidence must leave support unpromoted rather than being inferred from code presence.

For each supported `ManagedExternalEffect`, qualification must exercise:

- success;
- no-change;
- denial;
- stale evidence;
- executor failure;
- verifier failure;
- timeout/indeterminate outcome;
- duplicate delivery;
- restart before effect;
- restart after effect start;
- reconciliation.

## Q10 — multi-interface workstation experience convergence

v0.10 must prove that Linura's supported user interfaces are different views/invocation mechanisms over one typed machine model and one authority path, not parallel implementations with different privilege semantics.

Required evidence:

- **intent/state-centric:** current/desired state and causal intent shown by user-facing clients are derived from canonical authoritative records/evidence rather than private UI state;
- **control-plane-centric:** equivalent Linura-managed durable external mutations requested through CLI, Control Center, declarative configuration, command palette/shortcut, quick settings or accepted agent proposal converge on the same typed operation/intent and canonical Control lifecycle; lighter operation classes must still resolve to the same trusted registered semantics and Control-owned authority boundary where authority is involved;
- **agent/conversational:** agent requests remain proposal-only and produce no stronger authority than deterministic manual input;
- **manual/no-AI:** equivalent supported workflows remain available with all model providers absent;
- **Library/Setups/Profiles:** applicable Library operations are reachable from deterministic user-facing paths and retain exact revision/integrity semantics;
- **configuration-centric:** a versioned declarative configuration format is schema-validated, integrity/version bound where persisted/imported, previewable before mutation and incapable of carrying arbitrary shell, approvals, policy overrides or executor authority;
- **keyboard-centric:** supported interactive workflows expose keyboard navigation and essential shortcuts without hidden privileged command execution;
- **command palette/launcher:** palette entries resolve only registered typed Linura operations, intents, setups or explicit non-authoritative navigation/application targets; raw arbitrary privileged shell execution is not a supported palette action;
- **quick settings:** supported toggles/actions render authoritative/fresh state, represent unknown/stale state explicitly and use the same typed provider/Control path as equivalent deterministic operations;
- **desktop shell integration:** the qualified Hyprland session exposes coherent Linura entry points/status without granting the shell privileged executor or policy authority;
- **launcher/workspace UX:** application/action discovery and ephemeral workspace/window navigation work in the qualified session without being misrepresented as durable Linura-managed mutations;
- **notifications/OSD:** lifecycle notifications cannot report final success before independent verification/commit and must not leak secret-bearing material;
- **unified visual/theme system:** First Boot, Control Center, command palette/quick settings and supported notification surfaces consume the shared versioned Linura design/token foundation and first-party QML component layer rather than independent raw Qt styling; qualification additionally requires reviewed non-null visual baselines/captures for representative supported surfaces at representative resolution/scale states, executed visual comparisons, retained failure-diff artifacts, and paired interaction evidence. Shared tokens/components alone are not visual qualification;
- **accessibility/input parity:** every supported v0.10 end-user workflow can be completed with keyboard and pointer input, except any explicit release-contract exception; acceptance additionally covers screen-reader/semantic accessibility, focus/navigation semantics, reduced-motion behavior and supported display-scaling/HiDPI states;
- **resilient UI states:** supported graphical surfaces explicitly exercise offline/provider-unavailable, stale/unknown observation, recoverable error and reconnect/restart states without fabricating authority or success;
- **operation-class convergence:** equivalent requests from CLI, Control Center, config, shortcut/palette, quick settings and accepted agent proposal resolve to the same trusted registered `OperationClass`; interface/provider-supplied downgrade attempts are ignored/rejected;
- **risk-proportional ceremony:** operation class and trusted risk determine required machinery/ceremony; policy may allow low-risk operations to feel immediate while higher-risk operations surface review/approval, without changing underlying authority semantics;
- **transient-effect boundary:** any v0.10 transient external effect remains unprivileged and at most `UserState`, with Control mediation, authoritative preconditions, independent verification and audit; privilege/stronger risk/durable ambiguity causes managed promotion or an unsupported result;
- **failure/restart:** graphical/desktop surface restart reconstructs lifecycle state from authoritative records and cannot resurrect stale approval, fabricate success or replay an effect.

### Current Linura Shell / Control Center implementation boundary

The repository now contains the first `linura-shell` implementation candidate as one supervised Quickshell host for first-party workstation chrome. The bounded Control Center audio panel is a shipped Qt Quick/QML surface inside that host rather than an independent Control Center process. A narrow compiled `org.linura.ShellBridge` QML module is the only shell component that talks to Linura D-Bus APIs; QML itself does not own provider handles, executors, policy/risk selection, shell command execution or privileged authority.

The first-party panel also consumes the initial Linura QML UI Component SDK (`LinuraSurface`, `LinuraText`, `LinuraButton`, `LinuraSlider`) rather than carrying independent raw Qt visual styling. This is a consistency/qualification boundary only; the component SDK remains presentation-only and cannot grant or infer authority.

The audio panel retains the same authority invariants as the underlying qualified Session1 slice: authoritative Control1 observation, explicit freshness expiry, exact draft precondition binding, immediate pre-dispatch re-observation, exact-node Session1 invocation, receipt correlation validation, and independent post-effect authoritative re-observation before final success. Closing/restarting the shell cannot turn cached UI state or a receipt into authoritative success.

This v0.10 slice activates only trusted first-party shell surfaces. Plugin-shaped QML organization is a presentation/lifecycle mechanism, not a public extension permission model. Arbitrary user/third-party QML and security-sensitive hot reload are outside the support boundary until a separately qualified isolated capability-brokered extension runtime exists.

Qualification must freeze the exact Arch package snapshot and relevant Quickshell, Qt, Hyprland and Wayland identities used by the maintained workstation lane. Canonical Ubuntu CI may compile/install the Qt/D-Bus bridge and enforce static shell authority contracts, but it cannot substitute for real Quickshell/Wayland Q11 execution, visual evidence, keyboard/pointer/accessibility evidence, compositor/session restart behavior or package-compatibility proof. Landing this implementation therefore does **not** promote `linura-shell`, Control Center, `arch-hyprland-v1` or the PipeWire volume operation to release-qualified support.

The maintained workstation lane must also prove the session-supervision contract rather than infer it from unit installation: the qualified Hyprland startup path must activate `hyprland-session.target` and `graphical-session.target` (or an explicitly recorded equivalent systemd session manager must do so), `linura-shell.service` must become active through that target and remain `BindsTo`/`PartOf` it, and teardown must stop the shell with the graphical session. `HYPRLAND_NO_SD_TARGET` is outside the qualified native-Hyprland path unless equivalent lifecycle evidence is separately supplied.

The machine-readable Q10 gate is artifact-backed. `experience_evidence_ready = true` is valid only when the reviewed baseline files exist, the baseline manifest covers the contract's representative resolution/scale states, and a SHA-256-bound `qualification/v010/experience-evidence.json` records passing reviewed comparisons, retained reviewed failure-diff artifacts, and interaction/accessibility evidence for every required surface. Placeholder paths or undigested evidence cannot promote readiness.

v0.10 does not require a full Linura-owned replacement panel, lock screen, notification daemon or widget ecosystem. It does require the bounded desktop integration above. Existing qualified upstream components may remain outside Linura ownership where the release contract says so.

Negative/adversarial evidence must include:

- declarative configuration containing unknown fields, unsupported state, shell text, authority tokens or policy/approval material;
- shortcut/palette attempts to invoke unregistered or over-broad operations;
- operation-class substitution/downgrade attempts, including a privileged or SystemMutation+ effect falsely presented as transient;
- stale/unknown quick-setting observation and a concurrent external state change;
- forged/premature success notification or OSD state before verification;
- malformed/malicious GUI/palette/desktop requests attempting to widen authority;
- keyboard-only or pointer-only regressions in a workflow claimed to have parity;
- missing/invalid screen-reader semantics, focus order, reduced-motion behavior or representative HiDPI/display-scaling behavior;
- a null/unreviewed visual baseline, missing representative resolution/scale capture, missing interaction evidence, or an unretained visual failure diff;
- offline/error/reconnect UI states that hide stale/unknown authority state, fabricate success or become unusable;
- Linura Shell/Control Center panel/palette/desktop integration restart during an in-flight managed mutation;
- model provider absence while manual/configuration/keyboard paths remain usable.

## Release acceptance condition

A successful v0.10 qualification must demonstrate that an external experimental user can operate Linura meaningfully on the exact supported Arch/Hyprland workstation scope while preserving the same deterministic authority and recovery guarantees that protect headless v0.9.

Qualification must also prove the interaction invariant: intent, declarative configuration, Control Center, keyboard/command palette, quick settings, CLI and optional agent assistance are different interfaces to the same typed machine model and Control authority boundary. Trusted operation classification must be consistent across those interfaces. The desktop experience may vary its machinery/ceremony by operation class and risk, but it may not introduce an alternative authority path or downgrade a managed effect into a convenience fast path.

Passing tests without explicit interactive workstation evidence is insufficient. Passing interactive UI tests without deterministic lifecycle/failure evidence is also insufficient. Passing one polished interface while the required configuration/keyboard/pointer/manual convergence paths are missing is likewise insufficient. All required layers are necessary before `arch-hyprland-v1` may become release-qualified.


## Q9a — PipeWire/WirePlumber session-volume activation evidence

The first concrete transient workstation effect is bounded current-session output volume. Activation evidence must prove all of the following before this operation contributes to a release support claim:

- discovery may resolve `audio:session:default-output`, but mutation accepts only `audio:session:output:<numeric-node-id>`;
- authoritative observation records numeric node ID plus stable sink identity material and current volume;
- observation and mutation use the packaged root-owned WirePlumber `wpexec` helper rather than the human-oriented `wpctl` command surface;
- the Arch image profile pins `/usr/lib/linura/linura-session-audio.lua` to `root:root` mode `0644`, while runtime integrity checks independently reject symlinks, hard-link aliases, non-root ownership and group/world-writable helper bytes;
- the helper resolves exactly one `Audio/Sink` by the authorized bound node ID, `object.serial` and `node.name`, then invokes `mixer-api` in the same WirePlumber event-loop callback without yielding, so numeric-ID reuse cannot trigger a second external target lookup;
- execution is unprivileged, accepts only integer 0–100%, uses cubic user-volume scale, and cannot request amplification above 100%;
- the Session1 caller is bound to the authenticated session-bus principal/actor, must have the same Unix UID as the owning `linurad` session connection, and cannot supply operation class, risk, policy, provider or executor authority;
- a durable bounded SQLite/WAL audit reservation succeeds before executor dispatch and the terminal result is linked to that reservation; the database must retain its exact STRICT schema, single-link regular-file identity and configured growth ceilings;
- successful receipts require fresh authoritative post-effect observation strictly after dispatch start and exact postcondition verification;
- executor failure, observer failure, malformed helper output, helper substitution/integrity failure, stale/reused evidence, node replacement and audit reservation/terminal failure have adversarial tests and fail closed.

Landing this code does not by itself mark `arch-hyprland-v1` release-qualified; interactive workstation evidence remains required by the v0.10 release gate.
