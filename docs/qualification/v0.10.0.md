# v0.10.0 qualification — interactive Arch/Hyprland workstation

**Status:** planned; implementation and release evidence pending
**Claim class:** Experimental
**Target PlatformProfile:** `arch-hyprland-v1`

This dossier defines the evidence required before Linura may claim its first release-qualified interactive workstation PlatformProfile.

v0.9's Ubuntu 24.04/amd64/QEMU-TCG/headless lane remains an inherited **QualificationEnvironment**. It is not converted into a PlatformProfile by this milestone. v0.10 adds independent evidence for `arch-hyprland-v1`; passing the inherited Ubuntu lane alone is insufficient.

## Candidate identity contract

The candidate profile is:

- PlatformProfile ID: `arch-hyprland-v1`;
- machine class: `workstation`;
- distribution family: Arch Linux;
- init/service manager: systemd;
- session: Wayland;
- compositor: Hyprland;
- network provider: NetworkManager;
- Bluetooth provider: BlueZ;
- audio provider: PipeWire + WirePlumber;
- storage provider: UDisks2;
- authorization provider: polkit;
- filesystem/recovery baseline: Btrfs + Snapper.

Before release qualification, the evidence manifest must additionally freeze the exact Arch base/install source, immutable package snapshot or equivalent package-set identity, relevant package versions, kernel/session/graphics stack, exact Linura source/binaries and exact virtual/physical hardware evidence lanes.

`latest`, an unbounded rolling package set, or an unspecified hardware/driver combination is not a valid release evidence identity.

## Support-state transition

During implementation:

- `profiles/arch-hyprland-v1.toml` remains `status = "development"`;
- `hardware/support-matrix.json` keeps `machine_classes.workstation.release_qualified_profiles` unchanged;
- no UI, provider, executor or passing unit test may independently promote the profile to supported status.

Only protected post-release closure after immutable publication and independent verification may add `arch-hyprland-v1` to the release-qualified workstation lane.

## Q1 — source, profile and component contract

Required evidence:

- the target profile parses and validates under repository contracts;
- distro/compositor assumptions remain outside distribution-neutral core crates;
- exact provider/executor/verifier ownership is declared for every supported workstation effect;
- Linura Control Center is activated only when it is an unprivileged typed client;
- unsupported/planned components do not silently enter the release artifact/support claim;
- release artifacts derive from repository-owned component contracts;
- exact source SHA and profile revision are bound to qualification evidence.

Negative cases include malformed profile data, unknown provider identity, incompatible session/compositor, profile substitution and a component marked present without release activation evidence.

## Q2 — reproducible Arch substrate

A deterministic disposable qualification lane must prove that the candidate is built and exercised against a reproducible Arch package universe.

Required evidence includes:

- immutable base/install source identity;
- immutable package repository snapshot or equivalent exact package-set digest;
- exact installed versions for kernel, systemd, Hyprland, graphics/session dependencies and profile-critical providers;
- exact architecture and virtualization identity;
- exact candidate binary digests;
- rejection of substituted package snapshot/base source;
- no hidden dependency on mutable `latest` repositories during evidence production.

This lane proves deterministic system semantics but does not by itself prove real workstation graphics/hardware support.

## Q3 — workstation environment discovery and compatibility

Production discovery must construct live evidence and compare it against the candidate profile boundary without turning compatibility into a support claim. The typed assessment has exactly three outcomes: `ExactCandidateMatch`, `KnownMismatch`, or `InsufficientEvidence`. A known contradiction wins over incomplete evidence; otherwise any missing or ambiguous required fact yields `InsufficientEvidence`. Even `ExactCandidateMatch` remains candidate-only and cannot set release support.

For the current v0.10 candidate, positive identity evidence covers Arch, x86_64, systemd, Wayland, Hyprland, and the exact selected provider identities. Arch is rolling, so Ubuntu-style `VERSION_ID` is not a required PlatformProfile fact; exact package versions belong to the separately frozen Arch qualification substrate.

Production discovery is deliberately split across the canonical observation and Control boundaries. `linura-linux-observation` provides narrow bounded probes for distribution, architecture, init, one explicitly selected logind session/user, compositor, provider identity, audio and root filesystem. Each successful probe emits a canonical `ObservationEnvelope` with source-appropriate provenance such as filesystem, kernel/procfs, logind/native API, provider D-Bus health, user-systemd or Hyprland IPC. It does **not** aggregate those probes into a second observation model or a PlatformProfile decision.

The session-dependent probes accept a Control/composition-selected logind session identifier plus expected uid; they do not assume the collector process belongs to the target graphical session. Native file probes have explicit byte ceilings. D-Bus provider evidence requires the well-known service to be currently owned and to answer a direct bounded health probe; an activatable-only name is insufficient. PipeWire/WirePlumber evidence is bound to the selected logind user's runtime bus and active user-systemd units. A positive Hyprland compositor fact additionally requires a successful bounded response from a trusted socket under that selected user's logind runtime directory; `HYPRLAND_INSTANCE_SIGNATURE` is only a validated locator hint and never evidence by itself.

`linura-control` owns capability de-duplication, cross-fact compatibility aggregation, mismatch precedence and the final tri-state outcome over the resulting canonical envelopes. `linura-hardware` contains only the provider-neutral candidate contract, result types and single-fact assessment rules. Missing, stale, future, wrong-provider or incomplete canonical evidence remains `InsufficientEvidence`; duplicate capability evidence fails closed; a known contradictory fact remains `KnownMismatch`. These facts establish only live candidate compatibility. They are not hardware-lane qualification, package-snapshot evidence, mutation authority, or support-promotion evidence; those remain independently bound by the rest of this dossier.

Negative evidence must cover at minimum:

- another distribution;
- another compositor or X11 session;
- non-systemd init;
- unsupported architecture;
- missing/incompatible required provider;
- unsupported filesystem/recovery baseline where the release claim requires it;
- substituted hardware/driver/display lane;
- incomplete or ambiguous live discovery.

Unsupported or ambiguous environments remain visible but do not acquire support status or mutation authority.

## Q4 — First Boot, owner enrollment and recovery readiness

The v0.9 First Boot authority boundary is inherited and exercised on the workstation profile.

Qualification covers:

- interactive owner enrollment;
- durable restart-safe adoption state;
- deterministic default/Library/import source selection;
- exact source/revision integrity binding;
- fresh authoritative observation after source selection;
- deterministic fresh plan binding;
- stale/substituted source/session/observation/plan rejection;
- recovery readiness before workstation-ready state;
- native CLI/recovery escape hatch independent of Control Center;
- unsupported-profile failure before support-dependent mutation.

Historical plans, approvals and executor actions are never replay inputs.

## Q5 — Control Center authority isolation

Linura Control Center must be tested as an unprivileged protocol client.

Required evidence:

- no client-held privileged executor handle;
- no client-side generic root command path;
- no distro-specific direct mutation bypassing Linura providers/executors;
- policy/approval state originates from authoritative services, not UI fabrication;
- model output cannot become execution authority in the client;
- displayed execution success is not final until authoritative verification completes;
- reconnect/restart reconstructs state from durable authoritative records;
- CLI/protocol parity exists for supported authoritative operations;
- Control Center failure does not remove native recovery access.

Adversarial client input must not widen protocol authority.

## Q6 — manual end-user lifecycle

With all model providers absent, an experimental user must be able to complete the supported lifecycle:

```text
observe
→ express/select typed intent
→ deterministic plan
→ review policy/risk/approval requirement
→ authorize where permitted
→ durable prepare
→ narrow execution
→ independent verification
→ commit/audit
→ reconcile if needed
```

Required cases include:

- no-change/idempotent convergence;
- supported change success;
- deterministic preview;
- policy deny;
- approval required;
- expired/revoked approval;
- stale observation;
- stale plan;
- duplicate request;
- audit/explanation retrieval.

## Q7 — proposal-only agent assistance

The v0.8 boundary remains mandatory.

Qualification proves:

- model/agent input produces `IntentProposal`, not authority;
- uncertainty and assumptions remain visible;
- proposal acceptance performs deterministic validation before authoritative intent;
- provider timeout/failure/unavailability degrades to manual operation;
- malicious or over-broad proposal content cannot create executor/policy-admin authority;
- agent/UI restart cannot resurrect approval or executor authority;
- no supported workstation mutation depends on a model provider being present.

- deterministic impact preview before adoption;
- portable import/export integrity and version validation;

## Q9 — supported workstation capability domains

Every mutating domain included in the v0.10 release claim must independently prove:

- typed normalized desired state;
- authoritative observation;
- deterministic planning/diff;
- policy/authorization binding;
- durable prepare/idempotency;
- narrow privileged executor;
- independent verifier;
- commit/audit/reconcile behavior;

Candidate domains may include NetworkManager, BlueZ, PipeWire/WirePlumber, UDisks2, systemd lifecycle, package/update and Btrfs/Snapper integration. A domain that does not satisfy the full contract remains read-only or unsupported for v0.10.

For each supported mutating domain, qualification must exercise:

- success;
- no-change;
- denial;
- stale evidence;
- executor failure;
- verifier failure;
- timeout/indeterminate outcome;
- duplicate delivery;
- restart before effect;
- restart after effect start;
- reconciliation.

## Q10 — multi-interface workstation experience convergence

v0.10 must prove that Linura's supported user interfaces are different views/invocation mechanisms over one typed machine model and one authority path, not parallel implementations with different privilege semantics.

Required evidence:

- **intent/state-centric:** current/desired state and causal intent shown by user-facing clients are derived from canonical authoritative records/evidence rather than private UI state;
- **control-plane-centric:** equivalent Linura-managed durable external mutations requested through CLI, Control Center, declarative configuration, command palette/shortcut, quick settings or accepted agent proposal converge on the same typed operation/intent and canonical Control lifecycle; lighter bounded interactions must still resolve through the same typed authority architecture and may not create an interface-specific privilege bypass;
- **agent/conversational:** agent requests remain proposal-only and produce no stronger authority than deterministic manual input;
- **manual/no-AI:** equivalent supported workflows remain available with all model providers absent;
- **Library/Setups/Profiles:** applicable Library operations are reachable from deterministic user-facing paths and retain exact revision/integrity semantics;
- **configuration-centric:** a versioned declarative configuration format is schema-validated, integrity/version bound where persisted/imported, previewable before mutation and incapable of carrying arbitrary shell, approvals, policy overrides or executor authority;
- **keyboard-centric:** supported interactive workflows expose keyboard navigation and essential shortcuts without hidden privileged command execution;
- **command palette/launcher:** palette entries resolve only registered typed Linura operations, intents, setups or explicit non-authoritative navigation/application targets; raw arbitrary privileged shell execution is not a supported palette action;
- **quick settings:** supported toggles/actions render authoritative/fresh state, represent unknown/stale state explicitly and use the same typed provider/Control path as equivalent deterministic operations;
- **desktop shell integration:** the qualified Hyprland session exposes coherent Linura entry points/status without granting the shell privileged executor or policy authority;
- **launcher/workspace UX:** application/action discovery and ephemeral workspace/window navigation work in the qualified session without being misrepresented as durable Linura-managed mutations;
- **notifications/OSD:** lifecycle notifications cannot report final success before independent verification/commit and must not leak secret-bearing material;
- **unified visual/theme system:** First Boot, Control Center, command palette/quick settings and supported notification surfaces consume a shared versioned Linura design/token foundation sufficient to prevent incompatible per-surface visual contracts;
- **keyboard/mouse parity:** every supported v0.10 end-user workflow can be completed with keyboard and pointer input, except any explicit release-contract exception;
- **risk-proportional ceremony:** policy may allow low-risk operations to feel immediate while higher-risk operations surface review/approval, without changing underlying authority semantics;
- **failure/restart:** graphical/desktop surface restart reconstructs lifecycle state from authoritative records and cannot resurrect stale approval, fabricate success or replay an effect.

v0.10 does not require a full Linura-owned replacement panel, lock screen, notification daemon or widget ecosystem. It does require the bounded desktop integration above. Existing qualified upstream components may remain outside Linura ownership where the release contract says so.

Negative/adversarial evidence must include:

- declarative configuration containing unknown fields, unsupported state, shell text, authority tokens or policy/approval material;
- shortcut/palette attempts to invoke unregistered or over-broad operations;
- stale/unknown quick-setting observation and a concurrent external state change;
- forged/premature success notification or OSD state before verification;
- malformed/malicious GUI/palette/desktop requests attempting to widen authority;
- keyboard-only or pointer-only regressions in a workflow claimed to have parity;
- Control Center/palette/desktop integration restart during an in-flight managed mutation;
- model provider absence while manual/configuration/keyboard paths remain usable.

## Q12 — update, migration, power loss and recovery

The workstation claim requires fault-injected lifecycle evidence.

Required cases include:

- v0.9 → v0.10 persistent-state migration;
- writer-safe backup before risky migration;
- migration failure then restore/retry;
- candidate package/update interruption;
- authoritative re-observation after restart;
- crash before executor dispatch;
- crash after effect start;
- crash around durable commit;
- indeterminate external outcome;
- deterministic reconciliation;
- Btrfs/Snapper recovery where claimed;
- recovery with GUI unavailable;
- recovery with model/network unavailable where local material is sufficient;
- corruption and unsupported newer state fail closed.

The qualification harness must use process termination, reboot/power-loss or other failure injection appropriate to the effect being proved; process-local mocks cannot replace machine-level evidence where the support claim is machine-level.

## Q13 — workstation security baseline

The v0.10 candidate must preserve or strengthen inherited security properties:

- inbound firewall default deny;
- SSH disabled by default;
- explicit typed authority required to enable remote exposure where supported;
- untrusted package sources rejected;
- polkit/authorization boundaries validated;
- no generic privileged shell/API;
- actor/plan/evidence/session bindings fail closed on substitution;
- executor self-report never substitutes for independent verification;
- GUI/model surfaces have no stronger authority than the deterministic protocol;
- secret-bearing material is excluded from ordinary logs/audit/proposal diagnostics.

Threat-model tests must include malicious client/proposal/profile/import inputs and privilege-boundary attempts.

## Release acceptance condition

A successful v0.10 qualification must demonstrate that an external experimental user can operate Linura meaningfully on the exact supported Arch/Hyprland workstation scope while preserving the same deterministic authority and recovery guarantees that protect headless v0.9.

Qualification must also prove the interaction invariant: intent, declarative configuration, Control Center, keyboard/command palette, quick settings, CLI and optional agent assistance are different interfaces to the same typed machine model and Control authority boundary. The desktop experience may vary its ceremony by risk, but it may not introduce an alternative mutation path.

Passing tests without explicit interactive workstation evidence is insufficient. Passing interactive UI tests without deterministic lifecycle/failure evidence is also insufficient. Passing one polished interface while the required configuration/keyboard/pointer/manual convergence paths are missing is likewise insufficient. All required layers are necessary before `arch-hyprland-v1` may become release-qualified.
