# v0.7.0 security qualification — persistent declarative Library

**Status:** released; terminal release-security evidence complete.
**Terminal state note:** Security requirement language below is retained as the pre-publication security contract; terminal release evidence is authoritative.
**Claim class:** Experimental
**Supported platform profiles:** none

This review covers the new v0.7 persistence, portable-artifact and adoption attack surface while preserving the v0.6 privileged authority boundary.

## Security boundary

The local Library is non-privileged declarative storage. It cannot mint, import or restore human approval, policy authorization, executor authority, transaction authority, integrity keys, secret values or a privileged handle. Any adopted desired state that implies a machine change must re-enter fresh local observation, planning, validation and authorization and remains limited to the already-qualified v0.6 managed systemd active/inactive effect.

Models and agents remain proposal-only and receive no executor authority.

## Qualified input and persistence defenses

The corrected implementation proves:

- canonical constrained `namespace:name` secret references, including a 256-byte bound, are enforced consistently by Setup validation, persistence, portable encode/export and adoption;
- the public Setup JSON schema agrees with the Rust secret-reference contract;
- portable logical-ID/revision representations are canonicalized for ordering but reject missing, substituted or conflicting identities;
- conflicting revisions of one logical intent/setup are rejected across the complete reachable Setup/Profile closure;
- malformed, newer, cyclic, digest-tampered or colliding portable input fails closed before partial adoption;
- same-version alien SQLite databases cannot substitute for the Library schema;
- schema validation verifies canonical schema identity and foreign-key integrity before restore replacement;
- attacker-controlled SQLite schema metadata is preflight-bounded by object count, per-field/per-SQL size and aggregate SQL size before materialization;
- backup/restore rejection preserves the active valid destination;
- multi-record import/adoption is transactional and crash/failure injection does not leave partial current/history state.
