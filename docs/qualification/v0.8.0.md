## Required source-level tests

Implementation qualification must include focused tests for at least:

1. canonical proposal serialization is deterministic for semantically identical typed content;
2. supported proposal schema versions parse and unsupported-newer versions fail closed;
3. missing/unknown/duplicate/oversized fields are rejected before authoritative mutation;
4. executable shell text cannot substitute for typed capabilities;
5. model/provider output cannot assert approval, policy success or executor authority;
6. Linura Control constructs and minimizes semantic context before agent-runtime invocation, and secret canaries in raw Library/observation/retrieval/user data never reach runtime/provider input, proposal, diagnostics or audit;
7. deterministic mock provider produces replayable qualification fixtures;
8. provider timeout/cancellation/rate-limit/unavailability returns bounded non-authoritative failure;
9. malformed or truncated streaming output leaves authoritative intent unchanged;
10. prompt injection embedded in user/retrieved content cannot extend the capability registry or lower approval requirements;
11. stale observation revision is detected before proposal acceptance;
12. an observation that expires by time without a revision change is reacquired or causes acceptance to fail closed using trusted Control time;
13. stale policy/Library/capability-registry/existing-intent state is detected before acceptance;
14. capability references are resolved only against the current Control-owned registry;
15. acceptance decision identity/binding is exact-bound to principal + proposal ID/digest + accepted context + operation identity + create/revise action + exact target/revision expectation;
16. decision replay over changed proposal/context/operation/action/target material fails closed;
17. final authority/context/freshness/capability/decision revalidation is serialized with the durable linearization point, and concurrent authority drift cannot commit stale acceptance;
18. the authority-internal Library acceptance primitive requires a sealed Control-minted commit capability that is not constructible/deserializable through public SDK/client/provider surfaces;
19. direct public `LocalLibrary`/SDK attempts to fabricate proposal acceptance are rejected and leave durable state unchanged;
20. accepted proposal is converted only to a normal `Intent` in `Proposed` state through the sealed authority-internal acceptance path;
21. a process failure before commit cannot reconstruct the transient sealed capability from durable/public identifiers and must re-enter Linura Control;
22. a lost response after successful commit followed by restart returns the same durable `IntentId`/revision and exact acceptance record rather than creating a duplicate;
23. proposal/operation/decision identity reuse with changed principal, digest, context, action, target or resulting-intent expectation fails closed;
24. proposal rejection/revision leaves no partial authoritative intent;
25. no-provider/manual operation remains complete without weakening trusted acceptance checks;
26. material assumptions and uncertainty are preserved for review;
27. if multiple advisors ship, disagreement and source provenance remain independently inspectable;
28. any later managed effect still routes through v0.6 authorization and independent verification;
29. provider-generated explanation/rationale never overrides deterministic validation;
30. public Library persistence APIs remain usable for their existing v0.7 non-acceptance purposes without becoming an alternate proposal-acceptance authority path.

## Dedicated v0.8 qualification

A dedicated v0.8 workflow must run the exact candidate with deterministic provider fixtures, adversarial inputs, concurrency races and failure injection. External hosted-provider availability must not be a hard dependency for reproducible release qualification; provider-specific smoke tests may supplement but not replace deterministic adapter conformance.

Machine-readable evidence should record at minimum:

- exact candidate SHA;
- proposal schema/version;
- provider adapter identifiers exercised;
- deterministic fixture digests;
- adversarial scenario names/results;
- Control-owned pre-runtime secret-minimization/canary results;
- stale-context and timer-only observation-expiry scenarios/results;
- exact-bound acceptance-decision replay/substitution scenarios/results;
- final authority-serialization/concurrency scenarios/results;
- sealed Library direct-call rejection results;
- lost-response/restart idempotency and exact proposal/decision-to-intent lineage results;
- provider failure scenarios/results;
- explicit proof that no proposal restored or manufactured approval/executor authority;
- inherited v0.6/v0.7 qualification identities consumed by Trusted Release Proof.

## Release proof integration

Trusted Release Proof for v0.8.0 must fail closed unless:

- canonical CI, Security and CodeQL succeed for the exact release source;
- dedicated v0.8 proposal/agent qualification succeeds for the exact release source and covers every hardened acceptance invariant above;
- inherited mandatory v0.6/v0.7 lifecycle, authority, persistence, Library and recovery qualifications remain successful;
- release-preparation and metadata-only authorization preserve the reviewed tree;
- candidate artifacts reproduce and match declared digests;
- publication and independent verification remain bound to the exact authorized source.
