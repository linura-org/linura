## Required source-level tests

Implementation qualification must include focused tests for at least:

1. canonical proposal serialization is deterministic for semantically identical typed content;
2. supported proposal schema versions parse and unsupported-newer versions fail closed;
3. missing/unknown/duplicate/oversized fields are rejected before authoritative mutation;
4. executable shell text cannot substitute for typed capabilities;
5. model/provider output cannot assert approval, policy success or executor authority;
6. provider credentials and secret values are excluded from proposal/audit payloads;
7. deterministic mock provider produces replayable qualification fixtures;
8. provider timeout/cancellation/rate-limit/unavailability returns bounded non-authoritative failure;
9. malformed or truncated streaming output leaves authoritative intent unchanged;
10. prompt injection embedded in user/retrieved content cannot extend the capability registry or lower approval requirements;
11. stale observation revision is detected before proposal acceptance;
12. stale policy/Library/capability-registry revision is detected before acceptance;
13. accepted proposal is converted to typed durable intent through the v0.7 transaction/idempotency layer;
14. proposal rejection/revision leaves no partial authoritative intent;
15. changed semantic content cannot replay under an already-bound operation/proposal identity;
16. no-provider/manual operation remains complete;
17. material assumptions and uncertainty are preserved for review;
18. if multiple advisors ship, disagreement and source provenance remain independently inspectable;
19. any later managed effect still routes through v0.6 authorization and independent verification;
20. provider-generated explanation/rationale never overrides deterministic validation.

## Dedicated v0.8 qualification

A dedicated v0.8 workflow should run the exact candidate with deterministic provider fixtures and failure injection. External hosted-provider availability must not be a hard dependency for reproducible release qualification; provider-specific smoke tests may supplement but not replace deterministic adapter conformance.

Machine-readable evidence should record at minimum:

- exact candidate SHA;
- proposal schema/version;
- provider adapter identifiers exercised;
- deterministic fixture digests;
- adversarial scenario names/results;
- stale-context scenarios/results;
- provider failure scenarios/results;
- explicit proof that no proposal restored or manufactured approval/executor authority;
- inherited v0.6/v0.7 qualification identities consumed by Trusted Release Proof.

## Release proof integration

Trusted Release Proof for v0.8.0 must fail closed unless:

- canonical CI, Security and CodeQL succeed for the exact release source;
- dedicated v0.8 proposal/agent qualification succeeds for the exact release source;
- inherited mandatory v0.6/v0.7 lifecycle, authority, persistence, Library and recovery qualifications remain successful;
- release-preparation and metadata-only authorization preserve the reviewed tree;
- candidate artifacts reproduce and match declared digests;
- publication and independent verification remain bound to the exact authorized source.

## Terminal publication evidence

Terminal publication evidence is recorded here only by protected post-release closure after immutable publication and independent verification complete. Planning and implementation evidence do not substitute for that terminal record.
