# v0.6.0 security qualification — bounded managed authority

**Status:** implementation security review; terminal exact-source evidence pending.
**Claim class:** Experimental

This review defines the security properties that must remain true for the v0.6 managed systemd active-state capability. It supplements the general [`security-model.md`](../security-model.md), [`threat-model.md`](../threat-model.md), [ADR 0026](../adr/0026-bounded-v0.6-managed-mutation-authority.md) and the main [v0.6 qualification dossier](v0.6.0.md).

## Security claim

v0.6 introduces one bounded external mutation path. It does not introduce general root authority.

The only claimed managed effect is:

- canonical resource namespace: `systemd:unit:linura-managed-*.service`;
- desired state: exactly `active` or `inactive`;
- native effect: systemd `StartUnit(..., "replace")` / `StopUnit(..., "replace")`;
- public boundary: Experimental `org.linura.Authority1.ConvergeSystemdActiveState`.

Everything outside that boundary remains unsupported by this release claim.

## Trust-boundary review

### 1. Original caller

Threats:

- caller-supplied identity spoofing;
- assuming local/root means trusted human approval;
- replay/substitution under a previously approved operation ID.

Required controls:

- unique system-bus sender comes from authenticated D-Bus message metadata;
- sender must be a canonical unique bus name;
- OS principal is derived from that sender, not from method arguments;
- human approval is checked with fixed action `org.linura.authority.manage-systemd-active-state`;
- human provenance is created only after successful OS authorization;
- exact request identity/body is bound durably and changed-body reuse fails closed.

### 2. `linura-dbus` Authority1 adapter

Threats:

- transport grows into a second policy/orchestration layer;
- arbitrary D-Bus forwarding or systemd execution enters the transport crate;
- wire receipt leaks capability/secret material;
- checked XML diverges from live implementation.

Required controls:

- `linura-dbus` owns caller binding, Polkit interaction, wire conversion and service hosting only;
- no systemd executor, SQLite persistence or planner/policy ownership in `linura-dbus`;
- Authority1 handler remains abstract and delegates inward;
- canonical XML/live introspection must agree exactly for the method/signature;
- Authority1 remains registered Experimental in `contracts/stability.toml`.

### 3. `linura-authorityd` service identity/runtime

Threats:

- dedicated service identity becomes generic root capability;
- runtime composition layer accumulates domain policy and bypasses `linura-control`;
- durable state/secrets become accessible to ordinary clients;
- restart reconstructs process-local executor authority.

Required controls:

- daemon remains unprivileged under dedicated `linura-authority` identity;
- root execution remains in a separate service;
- planner/policy/transaction/recovery semantics remain in `linura-control`;
- protected authority SQLite state and integrity secrets are owned by the service boundary;
- process-local dispatch authority is non-serializable/non-reconstructible;
- restart enters durable recovery rather than reconstructing a handoff token.

### 4. Root systemd executor

Threats:

- direct caller bypass of Authority1/Control;
- generic root/systemd method proxy expansion;
- malformed namespace/state/binding substitution;
- executor self-attestation;
- dispatch timeout treated as safe no-effect.

Required controls:

- supported managed executor action is default-deny;
- production grant is limited to the dedicated authority service identity;
- ordinary users and root/admin direct calls do not automatically satisfy the managed executor authorization;
- executor revalidates exact namespace, state and deterministic binding;
- no shell, arbitrary executable, path/file write or generic systemd forwarding;
- native dispatch errors after ambiguity may be `Indeterminate`, never automatically interpreted as no dispatch;
- executor receipt is excluded as proof of final machine state.

### 5. Independent observation/verifier

Threats:

- executor reports its own success as state truth;
- stale/future/wrong-resource observation verifies success;
- verifier silently depends on privileged executor transport.

Required controls:

- fresh canonical systemd observation comes from the observation path, not executor receipt;
- verifier checks exact expected provider/resource/capability/postcondition and freshness/authority;
- verification failure/inconclusive state cannot commit;
- verification transport failure cannot trigger execution replay;
- post-commit reconciliation independently verifies/plans again.

### 6. Durable transaction/recovery state

Threats:

- stable operation ID rebinding;
- stale `Prepared` authority survives restart;
- blind replay from `Indeterminate`;
- recovery approval TOCTOU;
- conflicting recovery observers overwrite one another;
- reconciliation replays a committed effect.

Required controls:

- stable operation maps to `request:v06:<operation_id>`;
- exact canonical request is checked against durable `request_digest`;
- changed-body reuse fails `RecoveryRequestMismatch`;
- stale prepared authority is retired according to recovery state rules;
- `Indeterminate` cannot reconstruct dispatch permission;
- recovery constructs one exact fresh candidate and mints `FreshRecoveryApproval` against that candidate;
- current generation/state-version serialization rejects stale/concurrent recovery outcomes;
- conflicting state transitions to/retains blocked recovery rather than being overwritten;
- reconciliation retry is verification/planning only after commit.

## Polkit separation review

There are two distinct authorization questions:

1. may this original human caller submit the exact bounded managed request to Authority1?
2. may this service identity invoke the bounded root executor operation after Control has established fresh durable authority?

They must not collapse into one Polkit grant.

Human approval does not become an executor credential. Executor authorization does not prove that the request was policy-approved, freshly planned or safe to replay. The Control lifecycle must remain between them.

## Production policy vs qualification policy

Test-only principals/grants under `tests/acceptance/v06/` are allowed solely to exercise the disposable guest. They must not be installed as permissive product policy.

Canonical packaging must preserve default-deny behavior for the managed root executor and the intended Authority1 human approval semantics.

The obsolete broad root Polkit policy outside the canonical packaging path has been removed and must not return through duplicate packaging locations.

## D-Bus ABI review

Security-relevant D-Bus surfaces must be checked against both source and live introspection.

### Authority1

Expected:

- service/interface: `org.linura.Authority1`;
- path: `/org/linura/Authority1`;
- method: `ConvergeSystemdActiveState`;
- inputs: four strings;
- output: one structure `(sssssssssbas)`;
- stability: Experimental.

### Executor.Systemd1

The canonical XML must include the bounded `SetManagedActiveState` method actually implemented by the executor. A live privileged method absent from checked XML is a security-review failure even while Experimental.

## Component/layer review

`contracts/layering.toml` and `contracts/components.toml` must prevent architecture drift that could become security drift.

Required invariants include:

- `linura-control` does not directly depend on concrete SQLite/systemd transport adapters;
- `linura-dbus` does not own domain authority/executor semantics;
- `linura-authorityd` is a composition root, not a second semantic authority implementation;
- proposal-only agent components have no privileged authority role;
- future scaffolds cannot become release artifacts merely by being workspace members;
- privileged executor has an explicit bounded authority role.

## Real-system negative evidence

The disposable v0.6 guest must prove the security boundary with real system D-Bus/Polkit/systemd, including:

- unapproved human denial;
- ordinary direct executor denial;
- direct root/admin executor denial for the supported managed action;
- wrong namespace rejection;
- wrong desired state rejection;
- same operation ID / changed body rejection;
- exact retry without duplicate dispatch;
- verification-not-satisfied without false commit/replay;
- executor loss + authority restart without reconstructed dispatch;
- durable SQLite WAL/integrity checks.

## Deterministic fault/security evidence

The eleven-case matrix must additionally prove the failure windows that are difficult to force reliably through real system services on every run:

- stale evidence;
- executor failure/ambiguity;
- verifier transport failure;
- indeterminate execution;
- crash after handoff;
- safe re-prepare after proven no-effect;
- conflicting recovery blocking;
- post-commit reconciliation failure without execution replay.

## Release supply-chain security

`linura-authorityd` is a security-sensitive distributable binary in v0.6. Trusted Release Proof must include it in:

- sealed payload;
- SPDX SBOM;
- `SHA256SUMS`;
- provenance/attestation;
- independent byte-for-byte reproduction;
- published-release verification.

`linura-firstboot` is excluded from the v0.6 release payload because it remains a v0.9 roadmap scaffold; its presence would be a maturity/claim drift, not a security feature.

## Out-of-scope security claims

v0.6 does not claim security qualification for:

- arbitrary systemd management;
- package/file/network/storage/firewall/user/container/VM mutation;
- agent/model execution authority;
- remote/fleet control;
- supported distribution/hardware operation;
- transparent rollback of a coherently restored older authority database/VM snapshot;
- generic multi-resource transactional execution;
- Stable public mutation compatibility.

## Release-blocking security conditions

v0.6 must not publish if any of these remain true on the final exact source:

- Authority1/live XML/stability mismatch;
- root executor method/policy mismatch;
- direct executor bypass succeeds;
- human approval can be reused as executor authority;
- same operation ID can be rebound to changed request content;
- stale evidence can cross prepare/handoff/verify;
- executor receipt can cause verified commit;
- indeterminate restart can replay automatically;
- recovery candidate/approval binding is not exact;
- conflicting recovery is not serialized/blocked;
- required v0.6 VM/security gate is missing or red;
- `linura-authorityd` is missing from sealed/reproduced release material;
- a future scaffold is packaged/advertised as current capability.

Terminal security evidence must be recorded only after final exact-head and release-authorization runs actually succeed.
