## Claim under qualification

v0.6 is the first Linura milestone permitted to integrate the complete canonical managed-mutation lifecycle for one deliberately narrow external effect:

```text
request / intent
→ observe
→ plan
→ validate
→ authorize
→ prepare
→ execute
→ verify
→ commit
→ audit
→ reconcile
```

The qualified effect is limited to canonical `systemd:unit:linura-managed-*.service` resources and exactly the desired states `active` or `inactive`, dispatched through native systemd `StartUnit(..., "replace")` / `StopUnit(..., "replace")`.

The public mutation boundary is Experimental `org.linura.Authority1.ConvergeSystemdActiveState`. No generic apply, shell, package/file/network/storage mutation, arbitrary systemd method, agent execution authority, supported distribution/hardware or Stable API is part of this claim.

## Architecture under test

```text
system-bus caller
→ Authority1 caller binding
→ human Polkit authorization
→ linura-authorityd
→ ManagedLifecycleControl / durable authority
→ SQLite/WAL
→ separately authorized root linura-executor-systemd
→ systemd
→ fresh independent SystemdObserver/verifier
→ verified commit / audit / reconciliation
```

The test must prove the boundaries, not merely the final unit state.

## Deterministic v0.6 fault/recovery matrix

The repository-owned v0.6 qualification matrix uses real `SqliteTransactionStore` persistence and controlled authoritative observer/executor/verifier behavior. It records dispatch counts so no-replay/idempotency claims are externally observable inside the matrix.

Required cases:

1. inactive→active success + exact retry + request-substitution rejection;
2. active→inactive success;
3. denial/out-of-scope before dispatch;
4. stale evidence fails closed;
5. executor failure → durable indeterminate/no redispatch;
6. verifier transport failure → no commit/no execution replay;
7. indeterminate execution → no blind replay;
8. crash/restart after handoff → durable indeterminate/no reconstructed dispatch authority;
9. verification `NotSatisfied` → safe re-prepare semantics; restart retires stale `Prepared` authority;
10. conflicting recovery evidence → blocked;
11. reconciliation failure after commit → retry verification/reconciliation only, never execution replay.

The matrix passed on the final compacted implementation head, but that success is **not** the final release proof. Trusted Release Proof must run it again on the exact tree-identical release authorization after release preparation is merged.

## Recovery approval TOCTOU regression

The implementation must retain the corrected recovery flow:

1. acquire the exact fresh recovery observation;
2. construct the exact fresh recovery candidate once;
3. mint `FreshRecoveryApproval` against that same candidate;
4. consume the approval only for that candidate.

The test must fail if approval can be minted for one candidate and consumed against a subsequently reconstructed/different recovery candidate.

No stale/relaxed approval path is permitted.

### Real-system assertions

The exact release source must prove:

- `Authority1` live introspection contains `ConvergeSystemdActiveState`;
- executor live introspection contains `SetManagedActiveState`;
- unapproved human call is denied before execution;
- ordinary/direct root executor calls to the managed path are denied;
- wrong unit namespace and wrong desired state are rejected before handoff;
- inactive→active completes and produces exactly one fixture start dispatch;
- exact retry remains committed without a second start dispatch;
- same operation ID / changed body is rejected without a stop dispatch;
- active→inactive completes and produces exactly one fixture stop dispatch;
- already-satisfied/no-change behavior does not create an external effect;
- a fixture that does not retain the requested state causes verification failure rather than false commit;
- retry after that verification failure does not replay the previous execution blindly;
- executor unavailability around the handoff plus authority-process restart does not reconstruct old dispatch permission;
- the affected fixture remains unchanged after the unsafe retry attempt;
- authority SQLite state is in WAL mode and passes `PRAGMA integrity_check`;
- the deterministic eleven-case matrix passes inside the disposable guest.

The guest records real systemd dispatch markers so idempotency is proven through side effects rather than receipt strings alone.

## Qualification failure semantics

v0.6 qualification fails if any of the following is true:

- an eleven-stage success path skips/reorders a stage;
- same stable operation can execute twice;
- changed request content reuses prior durable authority;
- stale evidence can prepare/handoff/verify;
- human approval can directly authorize the root executor;
- an ordinary/root caller can bypass Authority1/Control via the managed executor method;
- executor acknowledgement can cause commit without independent observation;
- restart reconstructs a one-shot dispatch permit;
- indeterminate execution is automatically replayed;
- recovery approval is consumed against a different fresh candidate;
- conflicting recovery is overwritten instead of blocked;
- reconciliation failure replays the already-committed effect;
- Authority1 or executor live introspection disagrees with canonical XML;
- a future scaffold is packaged/advertised as an active v0.6 product component;
- release proof can build/promote while the v0.6 gate is absent or failed.
