# v0.8.0 release-preparation review — proposal-only agent interpretation

**Status:** planned; release-preparation review not yet complete.
**Claim class:** Experimental

This document defines the final cross-check required before a future reviewed `release: ready v0.8.0 — agent interpretation / IntentProposal` source may enter automatic mechanical release preparation. It is a planning contract and records no implementation or publication success by itself.

## Capability-boundary review

Before release readiness:

- [ ] implementation matches `docs/milestones/v0.8.0.md` and ADR 0028;
- [ ] `agent_role = "proposal-only"` remains exact;
- [ ] no provider/model receives executor, policy-admin or implicit user authority;
- [ ] Linura Control constructs/minimizes semantic context before it crosses into the agent runtime;
- [ ] accepted proposals enter authoritative state only through the dedicated v0.8 Linura Control acceptance boundary backed by an authority-internal sealed Library acceptance primitive; generic public `LocalLibrary::create_intent` alone is insufficient;
- [ ] external effects remain behind the inherited v0.6 authority lifecycle;
- [ ] manual/no-provider operation remains complete;
- [ ] platform support remains `none`.

## Proposal and provider review

- [ ] `IntentProposal` schema/version/canonicalization is explicit and bounded;
- [ ] assumptions, uncertainty and context/provider provenance are preserved where material;
- [ ] raw secret-bearing Library/observation/retrieval/user context never crosses into the untrusted agent runtime;
- [ ] provider adapters share one proposal contract and deterministic conformance fixtures;
- [ ] malformed/partial/oversized/unknown output fails closed;
- [ ] provider timeout/cancel/rate-limit/unavailability cannot partially mutate authoritative intent;
- [ ] prompt/tool injection cannot extend capabilities or lower approval requirements;
- [ ] secrets/credentials are excluded from runtime/provider request, proposal and diagnostic surfaces.

## Trusted acceptance review

- [ ] authenticated `Principal` is obtained independently from trusted transport/session state and proposal `Actor` remains provenance only;
- [ ] Linura Control re-reads/re-resolves all authority-bearing observation, policy, Library, capability-registry and existing-intent dependencies at acceptance;
- [ ] time-based observation freshness is evaluated using trusted Control time even when the observation revision is unchanged; expired evidence is reacquired or acceptance fails closed;
- [ ] current authority-context binding is Control-owned and must exactly match the proposal binding;
- [ ] capability references resolve only through the current Control-owned local capability registry;
- [ ] the applicable human/policy acceptance decision is Control-owned and exact-bound to principal + proposal ID/digest + accepted context + operation identity + create/revise action + exact target identity/revision expectation;
- [ ] the acceptance decision cannot be replayed over changed proposal/context/operation/target material;
- [ ] final context/freshness/capability/decision revalidation is performed at the durable linearization point under a Control-owned serialization/CAS boundary, and concurrent authority drift fails closed;
- [ ] while that boundary is held, Linura Control mints a sealed exact-bound acceptance-commit capability that is non-user-constructible/non-deserializable and consumed by the authority-internal Library persistence primitive;
- [ ] no public `LocalLibrary`/SDK method accepts caller-constructible proposal-acceptance authority material or can bypass the sealed Control capability;
- [ ] direct public Library/SDK attempts to create proposal acceptance are rejected and leave durable state unchanged;
- [ ] the authority-internal Library primitive atomically commits the intent transition and exact acceptance record;
- [ ] the durable acceptance record retains decision identity/binding plus exact principal/proposal/context/operation/action/target, authority-generation/freshness evidence and resulting `IntentId`/revision;
- [ ] exact retry after lost response/restart returns the same durable result and conflicting reuse fails closed;
- [ ] a crash before durable commit cannot reconstruct/reuse the transient sealed capability and must re-enter Linura Control for fresh authority establishment;
- [ ] acceptance creates only a normal `Intent` in `Proposed` state and grants no machine-mutation approval/executor authority.

## Qualification review

- [ ] exact-head CI succeeds;
- [ ] exact-head Security succeeds;
- [ ] exact-head CodeQL succeeds;
- [ ] dedicated v0.8 proposal/agent qualification succeeds, including Control-owned pre-runtime projection minimization, timer-only observation expiry, exact-bound decision replay rejection, concurrent authority-drift serialization, sealed Library direct-call rejection, and atomic lost-response/restart idempotency;
- [ ] inherited v0.6/v0.7 authority, durability, Library and recovery qualification remains green;
- [ ] every review finding is addressed and every review thread is resolved on the exact candidate head.

## Frozen release-contract review

- [ ] `docs/releases/v0.8.0.md` matches the implemented dedicated acceptance and proposal-only claim boundary;
- [ ] release wording is publication-stable and contains no transient current-state assertions;
- [ ] distributable artifact claims remain exact;
- [ ] known limitations and non-goals remain explicit;
- [ ] release contract does not widen platform support, executor scope or agent authority.

## Trusted Release Proof review

- [ ] metadata-only authorization is tree-identical to the reviewed preparation source;
- [ ] protected-main CI/Security/CodeQL are fresh for the authorization source;
- [ ] Trusted Release Proof includes dedicated v0.8 qualification and inherited mandatory release gates;
- [ ] deterministic build, digests, SBOM, proof receipt, attestations and independent reproduction remain exact-bound.

## Publication review

- [ ] tag-last publication uses the sealed payload without rebuild;
- [ ] immutable GitHub Release is bound to the exact authorized source;
- [ ] independent Release Verification redownloads and verifies published assets/evidence;
- [ ] protected post-release closure is reviewed before roadmap advancement;
- [ ] terminal current-release indexes/qualification state are synchronized by closure.

## Decision

A release-readiness commit is permitted only after every pre-publication checklist item applicable at that stage has exact evidence. Terminal publication/verification/closure items remain controlled by the automated release lifecycle and must never be marked complete merely to make a candidate appear ready.
