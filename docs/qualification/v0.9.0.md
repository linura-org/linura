### Q2 — source-path and provisioning semantics

Exercise the supported First Boot input classes:

| Source path | Required behavior |
| --- | --- |
| fresh intent | normalized source identity then exact target validation/discovery/observation |
| deterministic default | fresh target validation/discovery/observation; no hidden network/model dependency |

Negative cases include empty/control-character/oversized source identity, malformed or unsupported manifest fields/version, portable source with missing/malformed digest, digest supplied where forbidden, missing/substituted exact Library revision, source change after observation/plan, and malformed/corrupt/newer durable provisioning state.

Provisioning input may not carry shell snippets, generic commands, executor permits, approvals, policy overrides, historical execution transcripts, model authority or secret values.

### Q3 — exact reference-environment discovery

Discovery fails closed unless all candidate fields match the exact supported shape.

Required negative cases include:

- workstation/edge substituted for server;
- another distribution or release;
- `aarch64` substituted for `x86_64`;
- interactive desktop substituted for headless;
- KVM, bare metal or other virtualization substituted for QEMU TCG;
- non-systemd init/service manager;
- untrusted base-image origin or substituted base-image digest.

Production First Boot constructs live environment evidence rather than validating a hard-coded expected struct. Mismatch reporting preserves the expected/observed field so unsupported-platform evidence is diagnostic without being accepted.

Machine binding hashes protected machine identity together with DMI product UUID. A byte-for-byte disk clone under a different hardware UUID must reject copied bootstrap history.

### Q4 — fresh observation and deterministic planning

All non-recovery source paths converge on current target evidence:

1. select and persist the exact source/provisioning identity;
2. validate the exact reference environment;
3. obtain fresh authoritative target observation;
4. re-resolve exact Setup/MachineProfile revision where selected;
5. reconstruct desired state from that exact declarative source;
6. derive deterministic non-authorizing `ReconciliationPlan` material;

8. persist the generation-anchored plan binding before `FirstBootPlanning` can complete;
9. reject stale/substituted source or observation binding;

Historical execution transcripts and historical plans are never replay inputs.

### Q5 — pre-authority Control-submission isolation

Required evidence:

### Q7 — bootstrap sequencing, durability and restart

The bootstrap ledger proves monotonic completion across:

`base-environment verification → Linura installation → persistent-state initialization → security baseline → provisioning-mode selection → bootstrap-connectivity resolution → hardware discovery → source selection → target observation → First Boot planning → recovery checkpoint → owner-enrollment resolution → First Boot ready`.

Required cases include:

- normal ordered completion;
- repeated idempotent observation of already-complete prefix;
- skipped/out-of-order/corrupt/newer state rejection;
- restart at every prepared stage boundary;
- restart at every effect-started boundary;
- crash after generation-anchor staging;
- crash after durable ledger persistence;
- crash after generation-anchor finalization;
- recovery checkpoint restart/restore;
- exact complete-ledger handling;

The exact guest uses a persistent copied qcow2 and hard QEMU power cycles rather than process-only restart substitutes.

Generation anchoring protects ledger/state-root rollback while the machine-scoped anchor remains trustworthy. v0.9 does not claim coherent privileged whole-disk rollback resistance without future TPM/hardware/remote monotonic state.

## Production entry-point boundary

The release-exposed v0.9 production provisioning entry is `linura-firstboot --bootstrap <absolute-state-root>`. It selects the deterministic `prepare-for-another-owner` path and converges the canonical durable stages to authenticated `owner-enrollment-pending`. Interactive-owner, unattended-manifest and selectable recovery modes remain qualification/internal state-machine coverage and are not claimed as user-selectable production entry points in v0.9.

The production bootstrap may issue only `linura-firstboot-preparer-revocation-v1` evidence after directly proving the fixed preparer process/group/password/SSH/sudo postconditions. Final-owner enrollment signing remains outside First Boot. `--qualification-environment` derives its lifecycle status from the frozen workspace version: readiness builds report candidate status, while the mechanically prepared 0.9.0 release build reports `release-qualified-experimental`.

The canonical release-facing proof is black-box and starts from a fresh protected state root with hostile preparer authority present. The exact-source production `linura-firstboot --bootstrap <absolute-state-root>` entry point must itself converge the deferred-owner transition, create authenticated revocation evidence, and leave no effective preparer authority. Qualification then independently observes those externally visible postconditions, performs a persistent QEMU power cycle, invokes the same production entry point again against the same state root, and requires restart convergence without recovering historical authority. Qualification-only transition binaries remain supplemental fault-injection coverage for prepared/effect-started crash windows; they cannot substitute for this production-entry proof.

## Provisioning ownership and authenticated handoff

The exact guest qualifies four bounded resolution modes: interactive owner, prepare-for-another-owner, unattended local and recovery.

Owner-enrollment and preparer-revocation receipts use protected-key HMAC authentication, exact session/machine/operation binding and freshness checks at consumption. Production exposes verification; synthetic signing is restricted to tests/qualification harness.

Product bootstrap operations execute through `linura-preparer` while preparer authority is active. At boundary 12 the qualification harness does not perform the security transition: exact-source production First Boot terminates preparer processes, removes supplementary groups, locks the password, removes SSH and dedicated sudo authority, validates effective sudo policy, and mints the authenticated revocation receipt. The qualification identity is only an out-of-band launcher/observer that survives revocation of the preparation principal. After production returns, qualification independently observes process, supplementary-group, password, SSH, sudo-policy and protected receipt/key postconditions without reproducing the mutation algorithm. The transcript binds the actual preparation identity, production producer identity and independent verifier result.
