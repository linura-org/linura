# v0.9.0 qualification — First Boot and qualification environment

**State:** implementation and qualification in progress; the exact candidate environment has foundation qualification evidence, but v0.9 is not release-ready
**Claim class:** Experimental

This dossier defines the exact evidence required before Linura may publish the first bounded Experimental reference environment. The existence of this document, candidate code or passing unit tests does not itself create a platform-support claim.

## Exact candidate identity

The v0.9 candidate QualificationEnvironment is:

- QualificationEnvironment ID: `qualification/ubuntu-24.04-lts/amd64/qemu-tcg-headless`;
- machine class: `server`;
- distribution: Ubuntu 24.04 LTS;
- architecture: amd64 / `x86_64`;
- interaction model: headless;
- virtualization: QEMU TCG;
- init/service manager: systemd;
- base image: `https://cloud-images.ubuntu.com/releases/noble/release-20260725/ubuntu-24.04-server-cloudimg-amd64.img`;
- base-image SHA-256: `d1940f7d69d343355e183dff1e08a59852d32e7309baa7a4bad8365b11b005ac`.

Every acceptance run used as v0.9 release evidence must bind the exact source SHA, exact scenario revision/digest, exact base-image URL/digest, virtualization mode and toolchain/environment evidence. A different distro, image digest, architecture, interaction model or virtualization shape is separate evidence and cannot silently inherit this support claim.

While `v0.8.0` remains the current published release and has `platform_support = "none"`, `hardware/support-matrix.json` must retain both empty `qualification_environments.release_qualified` and empty PlatformProfile `release_qualified_profiles` lists. The support matrix may advance only during protected v0.9 release closure after the exact candidate has permanent verified evidence.

## Qualification layers

### Q1 — source and component contract

Required evidence:

- `linura-firstboot` is `integrated-experimental`, activation `v0.9.0`, authority role `client`;
- `linura-firstboot` is a release artifact and the release/image binary sets derive it from `contracts/components.toml`;
- `linura-bootstrap` and `linura-hardware` are `integrated-experimental`, activation `v0.9.0`, and are not independent release artifacts;
- component maturity remains valid before release while v0.9 is `next_release`;
- future Control Center, Shell and Agent UI components remain roadmap scaffolds outside the headless v0.9 boundary.

### Q2 — source-path semantics

Exercise all First Boot input classes:

| Source path | Required behavior |
| --- | --- |
| fresh intent | normalized source identity then target discovery/observation |
| deterministic default | fresh target discovery/observation; no hidden network/model dependency |
| Library Setup | exact local object/revision identity; fresh target discovery/observation |
| Library MachineProfile | exact local object/revision identity; fresh target discovery/observation |
| portable Setup | integrity-bound import; validation before use; fresh target discovery/observation |
| portable MachineProfile | integrity-bound import; validation before use; fresh target discovery/observation |
| recovery checkpoint | explicit recovery semantics; never treated as a new authority grant |

Negative cases:

- empty/control-character/oversized source identity;
- portable source with missing/malformed digest;
- digest supplied for a source class that must not carry one;
- source change after discovery/observation/plan invalidates every derived binding and prevents reuse of a prior Control submission;
- malformed/corrupt/newer portable artifact fails before any authority handoff.

### Q3 — reference-environment discovery

The discovery layer must fail closed unless all candidate fields match the exact supported shape.

Required negative cases include:

- workstation or edge class substituted for server;
- another distribution or release;
- `aarch64` substituted for `x86_64`;
- interactive desktop substituted for headless;
- KVM/bare-metal/other virtualization substituted for the QEMU-TCG candidate when the exact support claim is being evaluated;
- non-systemd init/service manager;
- untrusted base-image origin;
- malformed or substituted base-image digest.

Mismatch reporting must preserve the field, expected value and observed value so diagnostics do not collapse unsupported-platform evidence into a generic failure.

### Q4 — fresh observation and planning

All fresh/default/Library/import paths must converge on current target evidence:

1. select source;
2. validate candidate reference environment;
3. obtain fresh authoritative target observation;
4. bind a canonical plan to both the exact source revision/digest lineage and exact observation evidence;
5. reject stale/substituted source or observation binding;
6. require a new plan whenever source or authoritative observation changes.

Historical Setup/Profile execution transcripts or historical plans are not replay inputs.

### Q5 — pre-authority Control-submission isolation

First Boot stops before policy review, approval, denial and execution authority. It emits only an opaque, non-authorizing submission for Linura Control to evaluate independently.

Required evidence:

- First Boot exposes no caller-settable policy-review, approval or denial state;
- the selected source's exact Library revision or portable digest is domain-bound into canonical plan lineage;
- the canonical plan remains exact-bound to the retained current authoritative observation;
- substituted source/session/observation/plan/recovery lineage fails closed before submission;
- `ControlSubmission` fields are private and callers cannot construct or mutate authorization material;
- no First Boot type contains a privileged executor handle or constructible dispatch/approval permit;
- the submission contains no writable execution-authority bit and its compatibility accessor always reports false;
- after submission, Control independently performs canonical review/policy/approval/current-freshness and durable-authority checks;
- later mutation must still traverse the inherited v0.6 authority lifecycle.

Control-owned denial/approval behavior is qualified with the inherited Control authority layer, not by reintroducing a review state inside First Boot.

### Q6 — recovery checkpoint

A session cannot become ready for authority handoff until recovery is proven ready.

Required evidence:

- checkpoint identity is non-empty, bounded and path-safe;
- checkpoint SHA-256 is structurally valid and exact-bound;
- checkpoint and restored artifacts come from the qualified protected producer boundary rather than caller-selected equal files;
- restored artifact is a distinct path and inode, not a hard-link alias;
- trusted restore receipt is exact-bound to session, canonical plan, checkpoint ID and digests;
- producer directories/artifacts fail closed on symlink or unsafe ownership/permissions;
- native recovery access independent of First Boot/model/network is affirmative;
- missing/substituted restore proof or native recovery fails closed;
- checkpoint substitution after planning invalidates or fails the pre-authority submission as appropriate.

### Q7 — bootstrap sequencing and restart

The bootstrap ledger must prove monotonic stage completion across:

`base-environment verification → Linura installation → persistent-state initialization → security baseline → provisioning-mode selection → bootstrap-connectivity resolution → hardware discovery → source selection → target observation → First Boot planning → recovery checkpoint → owner-enrollment resolution → First Boot ready`.

Required cases:

- normal ordered completion;
- restart/resume at every stage boundary;
- repeated idempotent observation of already-complete prefix;
- skipped stage rejection;
- out-of-order/corrupt persisted ledger rejection;
- complete-ledger handling;
- interruption before/after recovery checkpoint;
- First Boot readiness rejected if any required pre-handoff stage is absent.

The in-memory monotonic ledger is implemented. Durable bootstrap persistence/restart qualification remains a release blocker.

### Q8 — installation security baseline

The candidate must fail closed if the Linura adoption baseline is weakened below the v0.9 contract.

At minimum prove:

- no guest disk-encryption claim is inferred from the pre-existing cloud-image substrate;
- inbound firewall default deny retained;
- SSH not silently enabled by default;
- untrusted package sources disabled;
- security-baseline state is established before First Boot readiness.

This contract does not itself claim a generic firewall/package mutation API.

### Q9 — offline and no-model path

The reference experience must remain operable without a model provider and without network access after required local installation material is present.

Disposable-system evidence must prove:

- `linura-firstboot --self-check` succeeds without provider configuration;
- deterministic default/Library/local import source handling requires no hosted service;
- stopping network connectivity does not remove native CLI/recovery access;
- no hosted catalog/sync service is required to understand a locally available portable Setup/Profile;
- no model/provider absence weakens review, recovery or authority binding.

### Q10 — exact disposable reference VM

The dedicated v0.9 acceptance workflow boots the pinned Ubuntu image under QEMU TCG, verifies its digest before launch, installs exact-source candidate binaries and emits source-scoped machine-readable evidence.

The merged First Boot foundation passed this exact-source disposable VM qualification before PR #125 merged. The workflow remains required on every later source change that touches the v0.9 qualification boundary; prior evidence cannot qualify a later source SHA.

Required evidence includes:

- distro/version/architecture/systemd/virtualization facts match the candidate contract;
- exact-source `linura-firstboot` binary is installed and self-checks;
- Linura Control/CLI inherited observation surfaces remain available;
- offline First Boot scenario succeeds;
- native recovery remains reachable independently of model/provider availability;
- exact acceptance scenario definition digest is recorded;
- exact candidate binaries and their SHA-256/size are recorded;
- base-image URL/digest and QEMU/toolchain versions are recorded.

A host-side mock alone is insufficient for the platform-support claim.

### Q11 — update, migration, backup and recovery

The v0.9 support claim requires durable-state evolution evidence, not just first install.

Source-level contracts now include:

- versioned durable migration ledger with corruption/newer-version rejection;
- atomic migration-ledger persistence after verification rather than before it;
- idempotent reopen semantics for already-applied migrations;
- validated independent backup requirements for risky migrations;
- canonical-path and device/inode checks that reject source reuse/hard-link backup aliases;
- byte-for-byte backup validation and immediate pre-apply revalidation;
- verification failure rollback for reversible migrations, with no durable success record;
- explicit manual-recovery escalation for non-reversible or failed rollback cases;
- `DurabilityUncertain` handling when an effect completes but its durable ledger commit does not;
- a versioned durable update journal with corruption/newer-version rejection;
- exact package transaction identity persisted at the prepare boundary;
- durable `Prepared → DispatchStarted → Verified` external-effect state;
- restart from `Prepared` may continue only the exact prepared transaction;
- restart from `DispatchStarted` requires re-observation and cannot reconstruct blind-replay authority;
- migration stage cannot follow package dispatch until independent verification succeeds;
- ordinary direct upgrade remains fail-closed except explicit coordinator or break-glass context.

These source-level contracts are necessary but **do not complete Q11**. Release readiness still requires exact-environment disposable-system evidence for:

- migrating supported prior Linura persistent state into the v0.9 candidate;
- preserving intent/Library/provenance semantics across migration;
- detecting unsupported-newer/corrupt schema before destructive mutation;
- restoring the validated backup after injected migration/update failure;
- interrupting update at deterministic checkpoints and recovering without blind replay;
- re-observing/reconciling an indeterminate update outcome rather than assuming success;
- exercising native recovery with First Boot/model/network unavailable.

See `docs/threat-model-v0.9-update-migration.md` for the source-level threat model and remaining adversarial qualification matrix.

### Q12 — inherited trust and authority

The v0.9 candidate must not regress released boundaries. Trusted Release Proof must retain, at minimum:

- v0.4 durability/ENOSPC and recovery evidence;
- v0.5 isolated executor/independent verifier evidence;
- v0.6 complete narrow managed-mutation lifecycle and disposable-system cases;
- v0.7 durable local Library/export/import/adoption evidence;
- v0.8 proposal-only agent interpretation and acceptance evidence;
- canonical repository, CI, Security and CodeQL gates;
- Control-owned post-submission review/denial/approval remains exact-bound to the canonical plan and current observation; First Boot cannot satisfy or forge it.

The platform-support milestone does not widen the existing managed external-effect namespace merely because a machine profile is now qualified.

## Security/adversarial cases

Dedicated v0.9 security qualification must include:

- malicious portable Setup/Profile labels/content cannot create authority;
- source/digest substitution;
- TOCTOU between source selection, observation, plan, pre-authority submission and Control review;
- unsupported-platform spoofing;
- stale discovery/observation use;
- recovery checkpoint substitution/corruption;
- attempts to skip bootstrap/security/recovery stages;
- loss of network/model availability;
- malicious First Boot input requesting shell/root execution;
- attempts to forge an authorizing First Boot submission or inject approval/dispatch authority;
- persistence corruption and downgrade/newer-schema cases;
- backup alias/substitution/corruption;
- migration verification/rollback failure;
- update interruption before and after external dispatch;
- indeterminate dispatch requiring re-observation rather than blind replay;
- diagnostics that avoid secret-bearing portable/Library content leakage.
