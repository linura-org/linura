# v0.10 S19 security qualification — BlueZ identity, pairing and trust

**Status:** Proposed adversarial acceptance; neither pairing authority nor physical hardware is qualified.
**Related:** [ADR 0049](../adr/0049-s19-bluez-bluetooth-authority.md), [domain qualification](v0.10.0-s19.md), [threat model](../threat-model.md).

## Security objective

No client, model, device advertisement, stale native object, unauthorized Agent1 callback or foreign system-bus sender may create a bond, accept a service, trust/forget a device, alter radio exposure, leak a PIN/passkey or fake independent verification. Bluetooth identity *before bonding* must not be represented as cryptographically authenticated by its name or address alone.

| Attack / failure | Required negative test | Independent proof |
| --- | --- | --- |
| BlueZ owner replacement | Restart `bluetoothd` between GetManagedObjects, prompt and effect | Owner epoch mismatch invalidates request/challenge |
| Adapter reset/hotplug | Swap controller, reuse `hci0`, change power/rfkill while planning | Native generation check; no migrated permission |
| Remote identity impersonation | Duplicate public address, random/private BLE address, same alias/name | Parent adapter, address type and bond continuity; prebond ambiguity explicitly disclosed |
| Malformed/oversized inventory | Duplicate native path, huge UUIDs/names, deep variants, many devices | Bounded fail-closed parser and complete inventory proof |
| Discovery session theft | Stop another client's discovery or treat combined filters as exclusive | Same native client/adapter/lease and cleanup without global stop |
| Forged Agent1 caller | Foreign D-Bus client invokes RequestConfirmation/AuthorizeService | Exact BlueZ unique sender and registered agent owner only |
| Wrong pairing target | Change adapter/device/service UUID/challenge after review | Purpose-bound immutable challenge and protected input, no cross-target approval |
| Unsolicited Just Works | Incoming automatic pairing with no independent approved request | Reject unless separately reviewed incoming policy; no implicit MITM claim |
| PIN/passkey leakage | Print, log, plan/audit, capture, model/prompts or secret store export | No plaintext key material outside protected native transport |
| Race/cancel/expiry | Agent Release/Cancel, session lock/seat change, duplicate/late reply | Revoked challenge cannot pair/trust/authorize |
| Authority downgrade | UI/agent claims pairing/trust/removal is transient or supplies risk floor | Trusted Control registry rejects changed class, principal and operation |
| Root/Polkit laundering | Foreign user/seat or ambient root invokes BlueZ action | Actual authenticated subject and native permission check |
| Trust/blocked confusion | Pair without trust, trust unpaired, block/unblock unexpected target | Explicit native Paired/Trusted/Blocked postconditions and bond revisions |
| Misleading connection | Connected but ServicesResolved false or requested service unavailable | Separate service/profile readiness after effect |
| Lost reply / repeated removal | BlueZ applies Pair or RemoveDevice then times out | Durable indeterminate attempt, observe-only recovery, no replay |
| Destructive bond deletion | RemoveDevice on another user's/shared device; mistaken alias | Exact device/bond identity, dependents impact and fresh deliberate review |
| Concurrent agent registration | Attempt global RequestDefaultAgent takeover or conflicting default agent | No ambient default agent; required ownership/exclusivity proof |
| UI/secure-session confusion | Shell crashes, user locks screen, new seat, display/power transition | No consent reuse, S17 lock and S21 power invariants intact |
| Mock/hardware confusion | Virtual HCI claims physical RF assurance | Evidence-class check rejects false Q11 promotion |

## Failure and recovery matrix

Exercise: before prepare; after durable reservation but before native dispatch; after effect initiation but before Agent1 reply; simultaneous pairing; canceled/late passkey; BlueZ owner death while bond persists; adapter rfkill; service absent; disconnect of one supported profile while others remain; restart with pending trust/removal; full/corrupt audit store. On every uncertain outcome: preserve causal attempt identity, invalidate stale challenge and approval, independently re-observe native bond/connection/service readiness, and never dispatch an implicit replay.

## Privacy and evidence limits

No raw PINs, passkeys, link keys, pairing transcripts or arbitrary peer metadata in audit, model, screenshots, diagnostic logs or retained qualification artifacts. Address, alias, advertised service/UUID and RSSI can identify people/devices and must be bounded and redacted when not essential. Virtual tests establish only their scoped behavior; native hardware proof and human confirmation must be recorded separately. No security proof is implied by this document or an inactive contract test.
