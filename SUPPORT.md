# Support

Linura is pre-1.0 experimental software. Community support is best-effort and does not constitute a production support SLA.

## Where to go

| Need | Channel |
|---|---|
| Reproducible bug | GitHub Issues |
| Compatibility problem on a specific system | Compatibility issue form |
| Concrete feature request | GitHub Issues |
| Usage or contributor question | GitHub Discussions — Q&A |
| Architecture/design exploration | GitHub Discussions — Architecture & RFCs |
| Proposal that needs a tracked design decision | RFC process in `docs/rfcs/README.md` |
| Suspected security vulnerability | Private reporting under `SECURITY.md` |
| Conduct concern | Private reporting under `CODE_OF_CONDUCT.md` |

Issues are for actionable tracked work. Discussions are for questions, exploration, ideas, and conversations that may or may not become tracked work.

Do not file suspected vulnerabilities in public Issues, Discussions, pull requests, or chat.

## Compatibility reports

A useful system compatibility report includes:

- distro and version;
- kernel;
- systemd version;
- compositor/session;
- relevant provider versions such as NetworkManager, BlueZ, PipeWire/WirePlumber, and UDisks2;
- exact Linura commit/version;
- selected PlatformProfile when applicable;
- capability snapshot;
- sanitized logs and reproduction steps;
- whether the behavior reproduces in a disposable or reference-qualified environment.

Remove credentials, tokens, private keys, machine identifiers, MAC addresses, serial numbers, account identifiers, and unrelated user data before attaching diagnostics.

## Scope of support

A successful build or a community-reported configuration does not expand Linura's supported platform boundary. Supported claims are defined by version-scoped release contracts and qualification evidence.

Sponsorship does not create a private support entitlement, response-time guarantee, roadmap priority, or security exception. Commercial support, if introduced later, must be documented separately from community sponsorship.
